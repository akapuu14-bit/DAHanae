# 部活コンシェルジュ タスクバックログ

作成：Takahiro（設計担当）　作成日：2026-09-27

## 0. 本書の位置づけ

`I-F契約.md`・`設計.md`・`仕様.md`・`実装計画.md`（体制：あかぷ=App/UI 40%、だーあさ=Data/Backend 40%、はなえ=PdM+一部実装 20%）を一次情報に、画面(S01-S10)・repository(9)・service(5)・ダミーデータのタスクを列挙する。各タスクに担当領域・対応SP/F・依存・推奨着手順・受入基準・触るファイル（所有境界）を付け、並行しても衝突しない粒度・順序にする。

**所有境界の原則**：1つのファイルは1タスク（＝1人）だけが新規作成・編集する。複数タスクが同じファイルに触れる必要がある場合は、その旨を明記し、後発タスクは先発タスクの完了後に着手する（同時編集しない）。

## 1. 推奨着手順（Wave）

並行して安全に進められる単位を4段階（Wave）に分ける。同じWave内のタスクは互いに依存せず並行可。次のWaveは前のWaveの完了が前提。

| Wave | 内容 |
|---|---|
| Wave 0 | DBスキーマ・Secrets雛形・`db/client.py`（他の全タスクの前提） |
| Wave 1 | repositories（9タスク、`services/errors.py`含む）／画面のモック実装（`screens/`はrepositories完成前でも、ダミーの戻り値でUIだけ先行着手可） |
| Wave 2 | services（5タスク、Wave1のrepositoriesに依存） |
| Wave 3 | 画面の実データ接続（`screens/*.py`をservicesに繋ぎ込む）／ダミーデータ投入 |
| Wave 4 | 結合（3名合流）・単体テスト添付・kurosuによる結合/システムテスト |

## 8. 衝突を避けるための運用ルール

- 同じファイルを複数人が同時に編集しない（上表の「触るファイル」は1タスク＝1所有者）。
- `services/*.py`・`repositories/*.py`はI-F契約.mdのシグネチャを変更しない。シグネチャを変えたい場合は、変更前にI-F契約.mdを更新してから着手する（先にドキュメント、後にコード）。
- `screens/*.py`はservicesの関数を呼ぶだけで、DB直接アクセス（repositories呼び出し）はしない。
