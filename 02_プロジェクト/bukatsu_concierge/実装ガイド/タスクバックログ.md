作成：Takahiro（設計担当）　作成日：2026-09-27

## 0. 本書の位置づけ

`I-F契約.md`・`設計.md`・`仕様.md`・`実装計画.md`（体制：あかぷ=App/UI 40%、だーあさ=Data/Backend 40%、はなえ=PdM+一部実装 20%）を一次情報に、画面(S01-S10)・repository(9)・service(5)・ダミーデータのタスクを列挙する。各タスクに担当領域・対応SP/F・依存・推奨着手順・受入基準・触るファイル（所有境界）を付け、並行しても衝突しない粒度・順序にする。

**所有境界の原則**：1つのファイルは1タスク（＝1人）だけが新規作成・編集する。複数タスクが同じファイルに触れる必要がある場合は、その旨を明記し、後発タスクは先発タスクの完了後に着手する（同時編集しない）。

## 1. 推奨着手順（Wave）

並行して安全に進められる単位を4段階（Wave）に分ける。同じWave内のタスクは互いに依存せず並行可。次のWaveは前のWaveの完了が前提。

| Wave | 内容 |
|---|---|
| Wave 0 | DBスキーマ・Secrets雛形・`db/client.py`（他の全タスクの前提） |
| Wave 1 | repositories（9タスク、`services/errors.py`含む）／画面のモック実装（`screens/`はrepositories完成前でも、ダミーの戻り値でUIだけ先行着手可） |
| Wave 2 | services（5タスク、Wave1のrepositoriesに依存） |
| Wave 3 | 画面の実データ接続（`screens/*.py`をservicesに繋ぎ込む）／ダミーデータ投入 |
| Wave 4 | 結合（3名合流）・単体テスト添付・kurosuによる結合/システムテスト |

**💬 ひとこと（タスク別）**

**T-B0S**

💬 これは何？（ひとことで）
　チーム全員が同じデータベース（Supabase）につながるための準備。これが無いと、各自のPCで作った部活・申込データがバラバラになり、画面どうしで同じ内容を見られない。

✅ 完成すると何ができる？
　- 全員が同じ部活・社員・申込のデータを見られる
　- 接続情報は各自の手元だけに置き、コードやファイルに直接書かない

**T-B00**

💬 これは何？（ひとことで）
　部活・社員・開催・申込などの情報を保存しておく「入れ物」を作る。これが無いと、どの画面も情報を保存も表示もできない。

✅ 完成すると何ができる？
　- 申込・開催・メッセージなど10種類の情報が保存できる状態になる
　- 同じ社員が同じ部活に二重に入る、同じ興味を二重に登録するといった誤りを、データベースの側でも止められる

**T-B01**

💬 これは何？（ひとことで）
　画面とデータベースをつなぐ「入口」を1つだけ作る。全員がこの入口を通して保存・読み出しを行う。これが無いと、どの機能もデータに触れない。

✅ 完成すると何ができる？
　- 画面を操作するたびに接続をやり直さず、データベースとやり取りできる
　- 接続情報は設定から読み込まれ、ファイルに直接書かれない

**T-B02**

💬 これは何？（ひとことで）
　接続情報を入れる欄の見本（雛形）を用意する。実際の値は各自の手元に置き、雛形には入れない。これが無いと、どの名前で接続情報を書けばいいか分からず、接続で迷ってしまう。

✅ 完成すると何ができる？
　- 必要な設定項目の名前が一目で分かる
　- 雛形を見て、自分の手元の設定ファイルを作れる

**💡 実装のコツ**

- `T-B0S`：💡実キーは絶対にコミットしない。共有はSecrets手順で行い、secrets.tomlがコミット対象に入っていないか最初に確認を。
- `T-B00`：💡2026-09-28に、applicationsは`status='申込済み'`条件付きの部分一意インデックスと、サービス層の事前存在確認を併用すると確定。キャンセル後の再申込は新しい行として許可する。
- `T-B01`：💡Streamlitは毎回再実行される。クライアントはモジュールレベルで1つだけ作り、各repoはそれをimportして共有する。
- `T-B02`：💡雛形には値を入れずキー名だけ。supabase_url/supabase_key/common_passwordをclient.pyと一字違わず揃えよう。

**💬 ひとこと（タスク別）**

**T-B03**

💬 これは何？（ひとことで）
　「パスワードが違う」「もう申込済み」などの“うまくいかなかった理由”を、どの機能でも同じ形で伝えるための共通の入れ物。画面がこの理由を見て、適切な案内文を出す。

✅ 完成すると何ができる？
　- 申込・ログイン・キャンセルの失敗が、理由つきで画面に届く
　- 失敗の理由の言い方が、どの機能でも同じ言葉で揃う

🔧 各要素の用途
　- `ValidationError`：入力もれ・選択肢にない値などの入力の誤り
　- `NotFoundError`：対象の部活・申込などが見つからないとき
　- `ConflictError`：申込済み・締め切り後など、今の状態と合わない操作
　- `AuthenticationError`：社員IDかパスワードが違うとき
　- `PermissionDeniedError`：その人には許されていない操作をしたとき

**T-B04**

💬 これは何？（ひとことで）
　社員の基本情報と、興味・経験を読み書きする部品。ログイン・人を探す画面・プロフィール画面の土台になる。これが無いと、人を探すこともプロフィールを見ることもできない。

✅ 完成すると何ができる？
　- 人を探すと、名前の一部でも社員が見つかる（大文字・小文字は気にしない）
　- 自分のプロフィールで、興味・経験や公開設定を編集して保存できる

🔧 各要素の用途
　- `get_by_id`：社員ID1人分の情報を取る。ログインにも使う
　- `search` / `count`：人を探す画面の検索結果と、「何件見つかった」の件数を出す
　- `get_interests`：プロフィールで興味・経験を表示する
　- `set_interests`：興味・経験の編集を保存する
　- `update_public_settings`：興味・参加可能時間の公開／非公開の切り替えを保存する

**T-B05**

💬 これは何？（ひとことで）
　活動の種類（部活の分野）の一覧を取り出す部品。部活を探すときの条件や、興味・経験を選ぶときの選択肢の元になる。

✅ 完成すると何ができる？
　- 部活を探す画面で、活動の種類を選んで絞り込める
　- プロフィールで興味・経験を選ぶとき、同じ一覧から選べる

🔧 各要素の用途
　- `list_all`：選択肢として並べる活動の種類の一覧を取る
　- `get`：1件の活動の種類の名前を引く（興味・経験の表示に使う）

**T-B06**

💬 これは何？（ひとことで）
　部活の基本情報（名前・拠点・活動時間・費用など）を読み書きする部品。部活を探す画面・部活の詳細・幹事の管理画面の土台になる。

✅ 完成すると何ができる？
　- 条件で部活を絞り込むと、該当する部活だけがカードで並ぶ
　- 幹事が自分の部活の情報を登録・編集できる

🔧 各要素の用途
　- `get`：部活の詳細画面に1件分の情報を出す
　- `search`：部活を探す画面の絞り込み結果を出す
　- `list_by_organizer`：幹事が自分の担当部活を一覧で見る
　- `list_all_for_admin`：運営者が全部活を一覧で見る
　- `create` / `update`：新しい部活の登録と、部活情報の編集・保存

**T-B07**

💬 これは何？（ひとことで）
　部活に所属しているメンバーを管理する部品。「この人は部活のメンバーか」「初参加か」を判断するときにも使う。

✅ 完成すると何ができる？
　- 部活の詳細で、今のメンバーが見られる
　- 幹事が社員を部活に追加したり、外したりできる

🔧 各要素の用途
　- `is_member`：その人が部活のメンバーかを判定する（申込時の初参加の判断にも使う）
　- `list_members`：部活のメンバー一覧を出す
　- `add_member` / `remove_member`：メンバーの追加と削除

**T-B08**

💬 これは何？（ひとことで）
　部活の「開催予定」をデータベースから取り出し、登録・変更する部品。これが無いと、部活の詳細に次の活動日を出せず、幹事も開催を登録・中止できない。

✅ 完成すると何ができる？
　- 部活の詳細に、今日以降の開催が日付の近い順に並ぶ（終わった開催は出ない）
　- ホームの「今週開催の部活」に、該当する部活が集計される
　- 幹事が開催を新規登録・編集・中止できる（中止から予定に戻すこともできる）

🔧 各要素の用途
　- `get`：開催1件の詳細（会場・日時など）を取る
　- `list_upcoming_by_club`：その部活の今後の開催一覧を日付順で取る
　- `list_upcoming_all_with_club`：全部活分をまとめて取る。ホームの集計用
　- `get_last_meeting_place`：直近の開催場所を取る。次回登録時の初期値に使う
　- `create` / `update` / `set_status`：開催の新規登録・編集・中止状態への変更

**T-B09**

💬 これは何？（ひとことで）
　申込の情報（誰が・どの開催に・どんな状態か）を保存・更新する部品。申込・キャンセル・申込一覧画面の土台になる。

✅ 完成すると何ができる？
　- 同じ開催に申込済みの人は、もう一度申し込めない
　- キャンセルした人は、同じ開催にもう一度申し込める
　- 自分の申込と、幹事に届いた申込が一覧に出る

🔧 各要素の用途
　- `get`：申込1件の情報を取る
　- `exists_active`：申込済みかどうかを判定する（二重申込を止める）
　- `insert`：申込を登録する
　- `update_status`：キャンセル・確認済みなど、申込の状態を変える
　- `has_past_non_canceled`：過去に参加したことがあるかを見る（初参加の判定に使う）
　- `list_by_applicant` / `list_by_organizer_club`：自分の申込一覧と、幹事に届いた申込一覧
　- `list_participants`：開催の参加者一覧を、初参加の印つきで出す

**T-B10**

💬 これは何？（ひとことで）
　申込した人と幹事のやり取り（メッセージ）を保存・表示する部品。申込ごとに会話が残る。

✅ 完成すると何ができる？
　- 申込ごとに、幹事と申込者のやり取りが古い順に並ぶ
　- やり取りの内容がデータベースに残り、画面を開き直しても消えない

🔧 各要素の用途
　- `list_by_application`：申込ごとのやり取りを古い順に取る
　- `insert`：メッセージを1件保存する

**T-B11**

💬 これは何？（ひとことで）
　「申し込まれた」「キャンセルされた」などのお知らせを保存し、既読にする部品。サイドバーの未読数と通知一覧の土台になる。

✅ 完成すると何ができる？
　- サイドバーに未読の件数が出る
　- 通知一覧に新しい順で並び、未読は太字になる
　- 画面を開くと、対象のお知らせが既読になる

🔧 各要素の用途
　- `count_unread`：未読の件数を出す
　- `list_by_recipient`：通知一覧に出す一覧を取る
　- `insert`：お知らせを1件作る
　- `mark_read`：種類を絞って既読にする（メッセージ画面を開いたとき）
　- `mark_read_all`：通知一覧を開いたとき、全部を既読にする

**T-B12**

💬 これは何？（ひとことで）
　検索・部活の閲覧・申込などの「操作の記録」を保存する部品。運営者が、どんな操作があったかを後から確認できるようにする。

✅ 完成すると何ができる？
　- 部活の検索・詳細の閲覧・申込完了が、社員ID・日時つきで残る
　- 同じ画面を何度も開き直しても、記録が増えすぎない

🔧 各要素の用途
　- `insert`：操作の記録を1件残す
　- `get_last`：直前の記録を取り出す（同じ操作を二重に残さないための比較に使う）

**💡 実装のコツ**

- `T-B03`：💡ConflictErrorには理由コード（not_open/already_applied）を持てる形に。画面がSP-31の文言を出し分けるのに使う。
- `T-B04`：💡employee_interestsもここで扱う（I-F契約0.2）。ID照合は大文字小文字を無視し、存在しなければ例外でなくNoneを返す。
- `T-B05`：💡マスタ参照だけの軽い層。get は存在しないIDでNoneを返し、例外にしない（repoの共通方針）。
- `T-B06`：💡検索は項目間AND・項目内OR。未指定の項目は条件にしない、かつis_active=trueのみ。組み立てはこの層に閉じ込める。
- `T-B07`：💡(club_id, employee_id)は一意。add_memberが二重に呼ばれても壊れないかを確認。is_memberは初参加判定でも使われる。
- `T-B08`：💡「過去を除く」の境界は今日を含めるか（今日以降）を仕様どおりに。開催日と時刻を混ぜず日付だけで比較する。
- `T-B09`：💡キャンセル後の再申込は別行になる。exists_activeはstatus=申込済みだけ見ないと再申込が弾かれる。二重insert対策は8章の保留。
- `T-B10`：💡やり取りは古い順で返す（SP-37）。applicationに紐づくので、キャンセル済みでも閲覧はできる前提で取得する。
- `T-B11`：💡未読はread_at IS NULLで数える（=NULL比較は誤り）。mark_readは種類を絞り、通知一覧用のmark_read_allと使い分ける。
- `T-B12`：💡get_lastは(employee_id, action)の最新1件。二重記録防止の比較はこれでDBから取る（session_stateは使わない）。

✅ 完成すると何ができる？
　- 実行すると、今のデータが消えて、同じ内容のダミーデータが入る
　- 毎回同じ結果になるので、テストを同じ条件で繰り返せる

## 8. 衝突を避けるための運用ルール

- 同じファイルを複数人が同時に編集しない（上表の「触るファイル」は1タスク＝1所有者）。
- `services/*.py`・`repositories/*.py`はI-F契約.mdのシグネチャを変更しない。シグネチャを変えたい場合は、変更前にI-F契約.mdを更新してから着手する（先にドキュメント、後にコード）。
- `screens/*.py`はservicesの関数を呼ぶだけで、DB直接アクセス（repositories呼び出し）はしない。
