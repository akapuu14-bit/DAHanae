# 部活コンシェルジュ テスト実行手順書

作成：yamapi（書記）　作成日：2026-10-10　対象：W3 のテスト実行（単体 U → 結合 I → システム S → 受入 A）

## 0. 本書の位置づけ

複数人・複数環境で、同じ手順・同じ記録様式でテストを回すための手順書である。

- テストの中身（前提・操作・期待結果）は `テスト設計.md` が正本。本書には写さない。
- 結果は `テスト結果.md` の該当行に記入する。凡例（未実行／合格／不合格／対象外）も同書 1章に従う。
- 役割分担は `00_ルール/V字フロー規定.md` の「左右の対応」表に従う。
- 本書は 5 文書（要求・要件・仕様・設計・テスト設計）に含まれない。本書の内容がテスト設計と食い違うときは、テスト設計が正で、本書を直す。
- 「仕様に書かれていません」と判断した点は補わず、止めて報告する（`V字フロー規定.md` の未決の扱い）。

## 2. 実行順

```
単体 U（偽repo・実装担当）→ 結合 I → システム S → 受入 A
```

- 前段に不合格がある間は、その機能に依存する後段を「合格」にしない（不合格の原因が前段にあるため）。前段の不合格と無関係な範囲は並行して進めてよい。
- 初回提出版は、単体・結合・システムの実行後に、コミット ID で固定する（`V字フロー規定.md`）。固定後に直した場合は、直したコミット ID と再実行の範囲を `テスト結果.md` 7.2 に書く。
- 実行前に、対象のコミット ID（`git rev-parse --short HEAD`）を控え、各結果の備考か証拠のログ先頭に残す。

## 3. 環境準備（人間側の前提作業）

実行の前提になる作業。AI スタッフは、これらが済んだ記録（担当者の申告と日付）が無い限り、I／S の実行を始めない。

### 3.1 ダミーデータの投入（だーあさ／あかぷの手元）

- 手順の正本は `実装ガイド/環境セットアップ.md`。
- 実行場所はリポジトリ直下。**まず `--dry-run` で内容を確認する。**

```bash
python scripts/reset_data.py --dry-run
```

- `--dry-run` を付けずに実行すると、接続先 DB の**全データが消える**（申込・メッセージ・操作履歴も含む）。実行前にチームへ声をかける。他の人がテスト中の DB に対して実行しない。
- seed は固定（N-08）。再実行しても同じデータになることを S-55 で確認する。
- 投入後の期待: 社員 500 名・部活 15 件（S-54）。件数は投入した人が記録に残す（証拠: コマンド出力）。
- 時刻依存テストのため、基準日を指定できる（`--base-date YYYY-MM-DD`）。指定した場合は日付を記録する。

### 3.2 仮認証 → 本物の認証への差し替え（#81、あかぷ）

- Issue #81 は 2026-10-10 時点で CLOSED。`app/frontend/mocks/` は origin/main に無いことを確認した（観察事実）。
- ただし #81 の受入基準のうち「本物の共通パスワードで E001 がログインできる」は、実 DB 接続での確認結果を本書では確認していない。**実行前に、あかぷが E001 でログインできることを確認し、日付を記録する。**
- 共通パスワードの値は、記録・ログ・スクショ・PR・Issue のどこにも書かない。スクショにパスワード欄が写る場合は、入力前か伏せ字の状態で撮る。

### 3.3 実行環境（実 Supabase DB）

- 接続情報は各自の `.streamlit/secrets.toml` に置く。**コミットしない。** `.env` と同様に秘匿値として扱う。
- テスト実行中のデータは架空データのみ。実データを入れない。外部公開（Issue #45 の前提）もしない。
- 複数人が同じ DB を同時に操作すると結果がぶれる。実行前に、誰がいつ実行するかをチームに知らせる。
- DB を初期化（3.1）したら、そのコミット ID・日付・実行者を記録する。初期化後に、前に取った証拠は再現条件が変わるため、必要なら再実行する。

### 3.4 実行前チェック

- [ ] 対象のコミット ID を控えた
- [ ] 3.1 ダミーデータ投入の日付・実行者を記録した
- [ ] 3.2 E001 でログインできる（実 DB）ことを確認した
- [ ] 他の人がテスト中でないことを確認した
- [ ] 秘匿値が手元の画面・ログに写らない設定になっている

## 4. 証拠の残し方

### 4.1 保存先（提案・要承認）

テスト結果の証拠は、次の場所に置くことを**提案**する。承認までは確定扱いにしない（0.1 の 3）。

```
02_プロジェクト/bukatsu_concierge/evidence/test/
  U/   単体の実行ログ
  I/   結合の証拠
  S/   システムの証拠
  A/   受入の記録
```

- サイズの大きい画像や動画を多数コミットしない。大きいものは PR のコメントに添付し、`テスト結果.md` の証拠欄に PR のリンクを書く。
- 秘匿値（パスワード・キー）、実在の個人情報が写っていないことを確認してから置く。

### 4.2 命名

`<テストID>_<YYYYMMDD>_<実行者>_<連番>.<拡張子>`

| 例 | 意味 |
|---|---|
| `I-041_20261012_kurosu_01.png` | I-041 の画面スクショ（1枚目） |
| `S-26_20261013_kurosu_01.png` | S-26 の画面スクショ |
| `U-003_20261011_terao.log` | U-003 の実行ログ |

- 日付は日本時間。同じ ID を同じ日に複数回実行したら、連番を増やす。
- 不合格の証拠も残す（上書きしない）。

### 4.3 `テスト結果.md` への記入ルール

1. 実行したら、**同じ日のうちに**該当行へ 合否・実行日・実行者・証拠 を記入する。
2. 合格は、証拠のパス（または PR／Issue のリンク）がある行にだけ書く。
3. 不合格は、備考に「期待: …／実測: …」を書き、`テスト結果.md` 7.2 に行を足す。原因が未確認なら「原因未確認」と書く。**原因を推測で書かない。**
4. 対象外は、備考に理由と根拠（テスト設計の節、または承認の記録）を書く。実行できなかっただけの場合は「対象外」にせず、未実行のままにして備考に理由を書く。
5. 再実行したら合否欄を最新に更新し、前回の結果を備考に残す。
6. 同じ `テスト結果.md` を複数人が同時に編集するとコンフリクトする。**区分ごと（U／I／S／A）に担当を分け、1 PR で触る区分を絞る。** コンフリクトしたら、後から出した人が最新の main を取り込んで、相手の記入を消さずに解消する。
7. 実行コマンド・環境・コミット ID を、証拠のログの先頭に書く。
8. 合否欄に書く語は 4 語（未実行／合格／不合格／対象外）のみ。

## 5. 区分別の実行手順

### 5.1 単体 U-xx（実装担当）

1. 対象の関数／モジュールを決め、`テスト結果.md` 4章に ID（`U-001` から連番）と対象を書く。
2. 偽 repo（DB を使わないスタブ）で service／関数を呼び、期待結果を確認する。
3. 実行ログを `U/` に保存する（4.2）。
4. 4章に、合否・実行ログ・実行者を書く。
5. 実行コマンドが定まったら、本書 0.1 の 1 を更新する。

### 5.2 結合 I-xx（Kurosu）

1. 3.4 のチェックを済ませる。
2. `テスト設計.md` 2章の各行の「前提」を作る（データ状態・ログイン者）。
3. 操作して、期待結果と照合する。画面の要件を満たす証拠として、スクショを撮る。
4. ★付き（重複申込防止・キャンセル/再申込・初参加判定・未読件数の算出範囲・非公開情報・権限・操作履歴の二重記録防止）は、**正常系と異常系・境界値のすべて**を実行してから、その観点を「完了」とする。
5. 内部の状態（DB の行、`confirmed_at` などの記録）を確認する I-xx は、確認した方法（画面／DB の参照）を備考に書く。
6. 4.3 に従って記入する。

### 5.3 システム S-xx（Kurosu）

1. 結合の主要な ★ が合格していることを確認する。
2. `テスト設計.md` 1章の各行を実行する。画面をまたいだ要件充足を確認する。
3. S-59 は設計上テスト対象外。N-01〜N-04, N-10 は実装レビューで扱う（`テスト結果.md` 7.1）。S-51（Could）は未実装なら「未実装」と備考に書く。
4. S-54〜S-56（データ件数・seed 固定・初期化ボタン）は 3.1 のダミーデータ投入と関係する。S-55 は初期化を複数回実行する性質上、他の人がテスト中でないときに行う。
5. 4.3 に従って記入する。

### 5.4 受入 A-xx（ユーザー）

1. 前提: S／I の結果が `テスト結果.md` に出揃っていること。未実行・不合格が残る範囲は、その旨を伝えてから受入に入る。
2. `テスト結果.md` 5章の手順を、ユーザー本人が操作する。期待結果と照らして、ユーザーが判定する。
3. ユーザー判定は、本人の言葉を欄に残す（AI が代筆して合格にしない）。所見があれば備考に書く。
4. 判定後の基準変更はしない。変える場合は理由・影響を ADR に書き、人の再承認を受ける（`V字フロー規定.md` 評価の節）。

## 6. 時刻依存のテストの注意

| 観点 | 対象 | 注意 |
|---|---|---|
| 日付の境界（JST） | I-018（今週0件）、I-033・S-18（過去の開催が出ない）、I-088・S-47（過去日の入力エラー）、I-008・S-53（週の境界） | 日付の基準は日本時間（Asia/Tokyo）。実行時刻が UTC で見える環境（CI・サーバー）と手元（JST）で「今日」がずれると、結果が変わる。実行環境のタイムゾーンを備考に残す |
| 初参加判定 | I-099〜I-102 | 判定はクラブのメンバー登録・過去の申込で決まる。投入データの状態が前提になるため、実行前に対象の社員・部活の状態を確認する |
| キャンセル期限の境界 | I-049・I-050・I-097・S-26 | 開始時刻より前までが可能で、ちょうど・超過は不可。**実行時に日付を固定**し、開始時刻の前後を作れる開催を用意して確認する（待って確かめるのではなく、データ側で開催時刻を調整する） |
| 「今日」「今週」 | I-017・I-019・S-11・S-53 | 基準日を決めて固定し、その日付を備考に書く。日をまたぐと結果が変わる |
| JST 早朝（0時〜9時）の境界 | 上記すべて | 日本時間の早朝は、UTC では前日にあたる。サーバー時刻（UTC）で日付を取る処理があると、日本時間の0〜9時にだけ「今日」が1日前になり得る。**この時間帯での実行と、通常の時間帯での実行の両方を、日付判定のテスト（上の日付の境界・初参加判定・キャンセル期限の行）で行う**。時刻は備考に書く |

- 日付の固定には、`reset_data.py --base-date` で投入データの基準日を決める方法がある（3.1）。アプリ側で日付を固定する方法が無い場合は、基準日に合わせて開催データを作る。固定の方法が決まったら、本書に追記する。
- 実行時刻に依存する結果は、実行日時（時刻まで）を備考に書く。同じ操作を別の時刻で再現できないときは、その旨を書く。

## 7. 実行中に問題が起きたら

| 状況 | すること |
|---|---|
| 期待結果と実測が違う | 不合格として証拠を残し、差分を 7.2 に記録。原因は推測せず「原因未確認」。修正は実装担当へ（Issue／PR） |
| 仕様に書かれていない挙動に当たった | 補って判定しない。「仕様に書かれていません」と報告して、その行は未実行のまま止める（`テスト設計.md` 5章に追記する提案を出す） |
| 環境（DB・認証）の問題で実行できない | 未実行のまま、備考に状況を書き、環境の担当（だーあさ／あかぷ）へ |
| 秘匿値が画面・ログに写った | その証拠を置かない・消す。すでにコミット・共有した場合は、god と運営へ即報告（値の変更が必要） |
| 他の人と DB 操作が重なった | 結果を信用せず、時間を分けて再実行。重なった事実を備考に残す |
