### 6.4 順序と依存

1. **T0a〜T0e（事前）**：コードを変えない準備。T0a→T0b→T0e は kurosu（T0e は人間が画面を見ている前で）、T0c は人間、T0d は takahiro。T0b の回数と T0e の時間の基準値が出るまで、T1 以降を始めない。
2. **T1 → T2 → T3**：影響の大きい順。T1（サイドバー固定分の6往復）は全遷移に効き、他の画面に依存しない。T2 は画面ごとに分け、T1 のあとに行う。T3 は T2 のあとに行う（一括取得にした関数にキャッシュを付ける）ほうが、無効化の対象が少なくて済むため。T3 の対象値は6.5の確定一覧による。
3. **T4**：T1〜T3 の各PRのあとに、回数と鮮度のテストを実行する。最後に回帰を通す。
4. **T5 → T6 → （T7）**：本番に反映したあとの再計測と、比較・判定。T7 は条件付き。
5. 実装は、タスクごとに1PR以上、人間がレビュー・マージする。

### 6.6 仮説検証としての位置づけ

採用する D-06・D-07・D-08 は、往復回数 N だけを減らし、1往復の時間 t_q は変えない。そのため、T0b（改善前）と T4・T5（改善後）の値を使い、**往復数の減少に比例して時間が減るか**を比べる（T6）。これは `2-cause-analysis.md` §2.1 の H1（距離）・H2（キャッシュなし×全体再実行）の検証にあたる。

- 比例して減る：時間の主因は往復（回数×1往復の時間）だった。H1・H2 を支持する。
- 比例して減らない：C8（Streamlit側の実行・描画）や H4（NANO）が残る証拠になる。撤退ライン（6.2）に従い、最終報告に記録する。
- 比較には、T0b の基準値（回数）と、時間の改善前の基準値が要る。時間の改善前の値は `1A-cloud-baseline.md` の n=1 の参考値しかないため、**改修前に T0e で2回取り直す**（変更前：5回）（PM決定。`7-plan-decisions.md` 追記④）。
