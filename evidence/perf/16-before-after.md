## 3. 1往復あたりの実時間の見積もり（実測ではない）

### 3.1 計算と前提

`(改修前の時間 − 改修後の時間) ÷ (改修前の往復 − 改修後の往復)` を遷移ごとに出した（上の表の15行、⑦の部活の管理起点は前の時間がないので除く）。D-06・D-07・D-08 は往復回数 N だけを減らし、再実行の回数（D-09 は未採用）は変えていないので、Streamlit 側の固定分（C8）が前後で同じなら、差は往復の分だけになる、という見立て（**推定**）。

### 3.2 結果

| 仮定 | 範囲 | 中央値 |
| --- | --- | --- |
| 改修前の往復が「小」 | 約108〜524ms | 約323ms |
| 改修前の往復が「大」 | 約77〜304ms | 約214ms |
| 両方を合わせた30値 | 約77〜524ms | 約268ms |

遷移ごとの値（小/大、ms）の例: ① 116/116、④ 108/108、⑤ 135/93、⑧ 278/214、⑩ 249/162、⑫ 378/216、② 345/197、③ 205/77、⑥ 323/283、⑭ 318/106、⑦（部活を探す起点）475/285。

### 3.3 読み方（確定と推定、限界）

- **推定**: 1往復の見かけ時間は、規模の仮定により数十〜約500ms、中央値で約200〜320ms。改修前の `T/N`（約234〜339ms、`2-cause-analysis.md` §3.3）と**同じ桁**で、矛盾しない。
- **この値は実測の1往復時間ではない**。次の理由で、遷移ごとにばらつき、1つの値には決められない。
  1. **本番の規模が未確認**。改修前の往復は偽データの小・大の2通りしか知らず、規模の仮定で値が約2倍動く。
  2. **T5 の時間は、ウォームで前の操作のキャッシュ（D-07）が効いた状態の値**。S-64 の「後」の往復は初回（キャッシュなし）の回数で、実際の往復はそれ以下。実際の往復が少ないほど、1往復の値は小さくなる（上の値は上側に寄る）。D-07 の命中率は未計測（D-07 の検証は偽 repo のみ、`14-d07-freshness-results.md`）。
  3. **改修後の時間は往復数ではほぼ説明できない**。T5 の時間と S-64 の往復の相関は約−0.09（①④は往復2で 659・883ms、⑫は往復11で 425ms）。固定分・キャッシュ・連打・測定条件のいずれかが効いている（どれかは**未確認**）。
- **T5 の注意の反映**: ①周2の前半（④⑭⑦①⑧⑩）は間隔ほぼ0の連打で、2回目が小さめに出ている可能性がある（④765・⑭1411・⑦567・①623・⑧640・⑩666）。②デプロイ版（Reboot 後・44d099e）は画面で確認していない。③手順書の「1遷移＝1回の呼び出し」から外れた箇所がある。**3.2 の値はこれらで動きうる**。

## 4. 仮説の検証

### 4.1 H1 米国↔東京の距離が遅さの要因（C2）

| 区分 | 内容 |
| --- | --- |
| 確認済み | Streamlit Community Cloud は全アプリを米国でホストし変更できない（公式 Docs。`memory` T0c）。Supabase は東京（PM）。距離の**前提**は成り立つ |
| 確認済み | 往復を減らした改修で、時間が大きく減った。例: ⑦ 5.2〜5.8秒 → 0.35〜0.61秒、⑫ 6.5秒 → 0.43秒、② 6.5秒 → 1.0秒。改修前の時間と往復（大）の相関は 0.84（15行） |
| 推定 | 往復数が時間の主因だったことを支持する。往復1回の見かけ時間（約77〜524ms、中央値約268ms）は、米国↔東京の遅延（約100〜170ms）に PostgREST 側の処理が乗った桁と矛盾しない |
| 未確認 | 往復1回の**実測**と、その内訳（距離・DB の処理・HTTPS の接続）。距離の寄与そのものは、D-10（実行場所の変更）をしていないため分けられない。Cloud の実行場所は設定画面に表示がない |

**判定: 推定どまり（根拠は強まった）**。「距離が主因」とまでは言えない。往復回数が主因だったことは、時間の変化から支持される。距離と DB 側の処理（H4）の切り分けは未確認。
