## 3. 推定の計算式と前提

### 3.1 式

```
遷移の待ち時間 T ≒ N × t_q + T_other
  N      : その遷移で発生するDB問い合わせの往復数（1B の値から数える）
  t_q    : 1往復あたりの時間
  T_other: Streamlit 側の実行・描画・WebSocket往復など（未測定）

T_other ≥ 0 なので、  t_q ≦ T / N   … 1往復あたりの「上限の目安」
```

### 3.2 往復数 N の数え方（1B の表から）

| 遷移 | 内訳 | N |
| --- | --- | --- |
| ホーム → 部活を探す（サイドバーのボタン） | 1回目の再実行: サイドバー3＋2回目の再実行: サイドバー3＋club_search画面2 | 8（1B のclub_search行そのまま） |
| 部活を探す → ホーム（サイドバーのボタンで戻る想定） | 1回目: サイドバー3（押した時点の再描画。画面はまだ出ない前提）＋2回目: ホーム15（小）〜23（大）。1B のホーム「1回描画」の値はサイドバー3を含む合計なので、2回目のサイドバー3は足さない | 18（小）〜26（大） |

- 戻りの操作は `1A-cloud-baseline.md` §1 でサイドバー「ホーム」と記載されており、この数え方と合う。ただしホームの表示規模（部活数C）は 1A に記載がなく、N の幅（18〜26）は小〜大の仮定のまま。
- 小/大は偽データの規模。本番の規模は未確認。
- 2026-10-15 修正（自己レビュー 2-4）: 旧版は戻りを21〜29と数えていた。1B のホーム15/23がサイドバー3を含む合計であることを見落とし、2回目のサイドバー3を二重に足していた。club_search への遷移に同じ数え方を当てると 3＋(3＋2)＝8 で 1B と一致し、ホームも 3＋15＝18（小）、3＋23＝26（大）が正しい。

### 3.3 見かけの1往復時間（上限の目安）

| 遷移 | T | N | T/N（t_q の上限の目安） | 確度 |
| --- | --- | --- | --- | --- |
| ホーム→部活を探す | 2069ms（n=1） | 8 | 約259ms | 推定 |
| 部活を探す→ホーム | 6096ms（n=1、条件不備） | 18〜26 | 約234〜339ms | 推定 |

- 2つの遷移の見かけ時間は、約259ms（部活を探す）と約234〜339ms（戻り）で、同じ桁にある。往復数に比例して時間が増える、という見立て（C1）と矛盾はしない。ただし**n=1ずつで、戻りは条件不備**であり、往復数の幅（小〜大の仮定）も広いため、2遷移が「揃った」とまでは言えない（確度は推定どまり。偶然の可能性が残る）。
- 距離との整合: 米国から東京までの往復遅延は、一般的な目安で東海岸が約150〜170ms、西海岸が約100ms前後。これにPostgREST側の処理と、HTTPSの往復（接続を使い回していれば1往復、使い回せていなければTLSの握手分が加わる）が乗ると、約234〜339ms（部活を探すは約259ms）は**大きくは外れない桁**。これは「Cloudが米国にある」という仮定の上の整合であり、Cloudの実リージョンは**未確認**（F5）。逆に、Cloudが東京にあれば1往復は十数msのはずで、この数字とは合わない。つまりこの整合は、距離（C2）が主因であることを支持する材料だが、証明ではない。
- 上限の目安とする理由: T には Streamlit の実行・描画・WebSocket往復（C8）が含まれるため、`T/N` は t_q を**多めに見積もった値**。実際の t_q は、これより小さい。

### 3.4 サイドバー固定分の寄与（見積もり）

```
サイドバー分の往復 = 6（遷移1回）
club_search への遷移:  6 / 8     = 75%（往復数ベース）
ホームへの戻り:        6 / 18〜26 ≒ 23〜33%
時間に換算（t_q 上限 約234〜339ms（戻り）／約259ms（部活を探す）なら）: 6 × 約234〜339ms ≒ 1.4〜2.0秒
```

- 時間換算は t_q の上限の目安をそのまま使った**上限寄りの推定**。実測 t_q が出れば置き換える。
- この見積もりは、サイドバー値の保持（§4 の D1）が効くとしたときの伸びしろの目安であって、効果の予測ではない。

## 4. 改善の方向性の候補と、減る往復回数の見込み

採否は決めない（段階3・6で人間が決める）。数値は1Bの偽データ規模での回数で、確度はいずれも「回数＝確認済みの構造からの試算、時間＝推定」。

| 候補 | 内容 | 減る往復の見込み | 前提・注意 |
| --- | --- | --- | --- |
| D1 | サイドバー値（未読件数・権限）を `session_state` に保持し、再実行ごとに取り直さない | 遷移1回あたり最大6往復（運営者4）。club_searchへの遷移は 8→2、ホームへの戻りは 18〜26→12〜20 | 未読件数の鮮度が落ちる。更新のタイミング（新着・既読化の直後だけ取り直す等）は仕様側の判断が要る（仕様に書かれていない） |
| D2 | `st.cache_data(ttl=…)` で読み取り結果を短時間保持 | 同一ユーザー・同一引数の再取得を省く。効く量は画面・TTL・更新頻度に依存し、今回は数えていない | 申込・既読など自分の更新直後に古い値を見せないための無効化設計が要る |

| D6 | 表示時の書込み（action_logs・既読化）を表示の後や非同期に回す | 遷移1回あたり書込み1往復分（該当画面のみ） | 記録の確実性（SP/要件上、ログが必須か）は文書に当たって確認が要る |

- 組み合わせの効果は掛け算で効くため、単純な足し算にならない。

## 5. まだ分からないこと

1. **Streamlit Cloud の実リージョン**（F5）。距離の整合（§3.3）の前提そのもの。確かめる方法の候補: Cloud上で外向き通信の遅延を1回測る、またはアプリ設定・ダッシュボードで確認する（実施は運営の承認範囲を確認してから）。Cloud の実行場所は、アプリの設定画面で確認できる（未実施。安価で、改修前に可能）。
2. **実測の1往復時間 t_q**（F14）。1Bの `perf_profile.py` は実DB向けで、人間判断で時間計測は打切り（2026-10-15）・未実行で残置。これが出れば `T/N` の「上限」が実値に置き換わり、C8（Streamlit側時間）の大きさも逆算できる。
3. **n=1 の代表性**。2069ms・6096msともに1回の値。ばらつき（初回アクセスの冷え、時間帯、同時利用）が不明。人間判断で打切り・n=1のまま（改善後に同手順で再計測）。
4. **戻り 6096ms の条件**。1A の記載で確認できたのは、操作がサイドバー「ホーム」であること、E001でログインした状態、ウォームのみ、計測中に hidden へ切り替わった疑いがあること（原因は未確認）まで。ホームの表示規模（部活数C）は不明のままで、往復数 N の幅（18〜26）はこれで決まる。
5. **本番データの規模**（部活数C・所属者M・開催E・申込A・社員P）。N+1の寄与（C5）は規模で大きく変わる。
6. **C8（Streamlit側の実行・描画）の大きさ**。T から N×t_q を引いた残りとしてしか見えない。
7. **NANO・接続数・コールドスタート**（C7）。CPU 2% の測定条件と、1往復ごとの応答時間はつながっていない。
8. **遅さの体感が「遷移」か「検索」か「表示」のどれに偏るか**（F1）。画面別の実測が揃っていない。
9. **接続の使い回し**。`create_client` は1回だが、HTTP接続（TLS）が再実行をまたいで使い回されているかは未確認。使い回されていなければ t_q が大きくなる。
