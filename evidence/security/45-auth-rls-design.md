## 0. 先に読む要点（8行）

1. 現状（確認済み）：RLS 無効、共有 anon キー、アプリ内の共通パスワード。DB 側は「誰の操作か」を区別できず、キー1つで全10テーブルを読み書きできる。
2. **最大の設計上の落とし穴（確認済み）**：`db/client.py` の Supabase クライアントは**モジュール先頭で1回だけ作られ、全ユーザーのセッションで共有**される。Supabase Auth のユーザーのトークンをこの共有クライアントに載せると、他のユーザーの権限で動く事故になる。**ユーザーごと（Streamlit のセッションごと）にクライアントまたはトークンを持つ**構成が必須（4章・6章）。
3. **同じ理由で D-07 のキャッシュ（`st.cache_data`）は全員で共有**される。RLS で見える範囲がユーザーごとに違うと、あるユーザーの結果が別のユーザーに返る恐れ。キャッシュのキーに「見る人」を含めるか、全員同じ結果の値だけをキャッシュする（6章）。
4. 認証方式は **A（Supabase Auth の email＋パスワード。社員ごとの初期パスワード。共通パスワードは廃止）を推奨**（3章）。社員に実メールアドレスはなく、B（メールのリンク）は使えない。C（共通パスワードを残してアプリが署名する JWT）は、署名用の秘密をアプリに置くことになり、非推奨。
5. 他人あての通知の作成（申込→幹事あてなど）と、他人の申込の件数表示（部活詳細の参加人数）は、単純な「自分の行だけ」ポリシーでは動かない。**DB 側の関数（SECURITY DEFINER）が必要**（5.4、未決は 13章）。
6. 列の公開設定（`interests_public`・`slots_public`）は行のポリシーでは隠せない列がある（`employees.available_slots`）。`is_admin` を本人が書き換えられない対策も要る（5章）。
7. 性能：**往復回数は変わらない**（RLS はサーバー内の処理）が、1往復の時間・ログイン時の往復は増えうる（**推定**）。D-06〜D-08 の前提は一部変わる。適用後の再測定計画を 7.1 に置いた。
8. 本番には直接適用しない。**別の Supabase プロジェクトで先に試す**（8章）。プロジェクト作成・鍵の発行・社員アカウントの作成は人間の ToDo（8.2）。未決事項は 13章（PM が選ぶ）。

### 3.1 推奨 A の詳細（案）

- **Auth ユーザーと `employees.id` の対応**：次のどちらか（13章 #2 で PM 選択）。
  - 推奨：`app_metadata`（サーバー側だけが書ける領域。**`user_metadata` は本人が書き換えられるので使わない**）に `employee_id` を持たせ、あわせて `employees.auth_user_id uuid unique references auth.users(id)` 列を追加する。ポリシーは `auth.uid()` から `employees.auth_user_id` を引いて社員IDを得る関数 `current_employee_id()` を使う（クレーム書換えの影響を受けない）。
  - 代替：JWT の `app_metadata.employee_id` クレームだけで判定（列の追加なし。引き当て不要で速いが、クレームが古くなると反映が遅れる）。
- **初期ログインの方法**：運営が発行スクリプト（開発者の PC で実行。service_role は PC 上のみ）で 500 件のアカウントを作り、社員ごとの初期パスワードを配布する。初回ログイン時にパスワード変更を促すか（未決、13章 #3）。
- **既存の共通パスワード**：切替の日に廃止（Secrets から削除）。切替の間は、検証用環境だけで A を動かし、本番は共通パスワードのまま（8章）。
- **ログアウト**：`sign_out` ＋ `session_state` の破棄。パスワード誤りの文言は SP-11 のまま（どちらが誤りかを示さない）。
- **セッションの更新**：アクセストークンは短命で、リフレッシュトークンで更新する。Streamlit のセッションごとに保持し、期限切れ時の再ログインの扱いを決める（実装時の確認事項、**未確認**）。

### 5.4 単純なポリシーでは動かない箇所と対応案

1. **他人あての通知の作成**（確認済み）：申込→幹事あて、キャンセル→幹事あて、メッセージ→相手あて、スタンプ→申込者あて、中止→申込者全員あて。`recipient_id = me` では INSERT できない。対応案：（a）INSERT の WITH CHECK に「`application_id` または `event_id` を通じて自分が当事者で、宛先がその相手」を入れる／（b）通知の作成を DB トリガ（申込・メッセージ・中止の INSERT/UPDATE を契機）に移し、アプリからの INSERT を禁止する。（b）が堅いがアプリ側の変更が大きい（`notify` の5か所を除去）。推奨は（a）。選択は 13章 #6。
2. **部活詳細の参加人数・参加者**（確認済み：`list_participants(event_id)`、件数表示）：一般社員が他人の申込を SELECT できなくなる。対応案：件数だけを返す関数（RPC：`event_application_counts(event_id)`）と、参加者の表示範囲を仕様で確認（氏名を一般社員に見せているか。**仕様の確認が必要**）。13章 #5。
3. **`employees.available_slots` の公開設定**（確認済み：SP-49 は現在アプリ側のフィルタ）：行ポリシーは列を隠せない。対応案：（i）現状どおりアプリ側のフィルタ（認証済みユーザーが API で直接読めば全員分が見える＝N-12 の「公開設定に応じてのみ」を DB で強制できない）／（ii）公開用ビュー `employees_public`（非公開の列を NULL にする）を作り、`employees` の直接 SELECT を絞る。13章 #8。
4. **`is_admin` の自己昇格の防止**：UPDATE ポリシーが「自分の行」を許すため、列を限定しないと自分を運営者にできる。列権限（`update` を許す列の限定）またはトリガで防ぐ（必須）。
5. **upsert**（`club_members.add_member`・`employee_interests`）：INSERT と UPDATE の両ポリシーが要る。`ignore_duplicates` の挙動は検証環境で確認（**未確認**）。
6. **埋め込み select（D-08）**：関連表にもそれぞれの SELECT ポリシーが適用される。埋め込み先が RLS で見えない行は欠ける（エラーでなく欠落）。画面ごとに期待どおりか確認が要る（テスト 9章）。

### 5.5 SQL 案の置き方

本書には SQL を載せない（実行も実体化もしない）。実装段階（T-S2）で `supabase/migrations/` に番号付きの新しいマイグレーションとして書き、検証環境にだけ適用する。既存のマイグレーションは書き換えない（`202609300001` と同じく追加適用）。

| # | 論点 | 選択肢 | 推奨 |
