アクセススピード改善ナレッジ（遅い画面を数えて直した話）

対象読者: チームメート（初心者〜中級）。Streamlit と Supabase を使って画面を作る人

読み終えたらできること: (A) 自分の画面が遅いとき、原因を調べる手順を踏める。(B) 今回の改善（D-06 / D-07 / D-08）の考え方を、これからの実装に使える

記録: yamapi（書記）／ 作成日: 2026-10-16 ／ 根拠: evidence/perf/17-final-report.md、docs/adr/ADR-PERF-01-性能改善方式選定.md、evidence/perf/ の各表。数値は最終報告どおりで、この教材では再計算していません

【確認状況】 推定は「推定」、未確認は「未確認」と書きます。時間は代表遷移のみ・各2回の測定です。結果は「全部速くなった」ではなく、「7遷移は目標内、4遷移は時間未達」です（5章）。

1

背景: 「遷移が遅い」

発表後に、チームの人から次のフィードバックが出ました（2026-10-15）。

「Streamlit Cloud で全画面の遷移が遅い、検索も表示も」

この時点で分かっていたことは少なく、数値の計測値は付いていませんでした。

  • 要件に、速度（待ち時間）の要件はありませんでした（N-01〜N-14）。つまり「何秒なら合格か」が決まっていませんでした。
  • st.cache_*（Streamlit のキャッシュ機能）は 0 件でした。
  • Supabase は東京、インスタンスは NANO、CPU 使用率は 2%（測定した日時・方法は不明）。

そこで、「感覚で直す」のをやめて、測る → 原因を絞る → 目標を決める → 直す → 同じ方法で測り直すという順番で進めました。

2

課題分析: 「往復」を数える

まず「往復」とは何か（電話のたとえ）

このアプリは、画面を動かす Streamlit Community Cloud（米国で動く。場所は変えられない）と、データを持つ Supabase（東京）が、離れた場所にあります。画面が表示されるたびに、Cloud から Supabase へ「この部活の一覧をください」と問い合わせが飛びます。

電話のたとえ: 米国の事務所から東京の倉庫に電話をかけて、「在庫を教えて」と聞き、答えを聞いて電話を切るまでが1回の往復です。1回の電話は短くても、10回かけ直せば、その分だけ待たされます。画面の表示が遅いとき、まず疑うのは「電話を何回かけているか」です。

数えてみたら

偽データのアプリで、画面が使う問い合わせの回数を数えました（本番のデータでの数え直しは、規模が違うため未確認です）。

見つけたこと中身
サイドバーが毎回問い合わせている画面を切り替えるたびに、サイドバー（未読件数・権限の判定）だけで6往復（運営者は4）。画面が2回描き直されるため、3往復が2回走る
件数に比例して増える（N+1）「部活1つにつき問い合わせ1回」のような作りだと、部活が増えるほど往復が増える。ホーム・社員検索・部活詳細など6画面で確認
表示のたびに書込みが走る画面がある部活検索・部活詳細・メッセージ画面で、表示の途中に書込み1往復
3回以内に収まる遷移改修前は0件（例: 部活を探すは8往復、人を探すは24〜36往復）

目標を数字で決める

「速くする」だけでは、いつ終わるか分かりません。そこで、人間（PM）が次の目標を決めました。

  • 時間: 主要な遷移で、中央値 1.0 秒以内・最大 2.0 秒以内（Streamlit Cloud・起動済みの状態）。
  • 往復の回数: 遷移1回あたりの読取往復に上限を置く。最初の案は3回（根拠: 1000ms ÷ 1往復およそ260ms ≒ 3.8）。のちに遷移ごと・社員の種類ごとの上限になりました。

時間は Cloud でしか測れず、条件がそろえにくい一方、往復の回数は手元で何度でも同じように数えられるのが利点です。回数を補助の目標にしたので、テストで必ず確かめられます。

1往復の実時間は一度も実測していません。 「1往復およそ260ms」は、実測した時間を往復数で割った「見かけの時間」で、Streamlit 側の時間も含みます。実際の1往復はこれより短い、という目安の数字です。

3

仮説（H1〜H4）と、検証の結果

最初に立てた原因の仮説は4つです。推定どまりのものは推定と書きます。

仮説内容改修後の判定
H1米国↔東京の距離が遅さの要因推定どまり。往復を減らすと時間が大きく減ったので、往復回数が主因だったことは支持される。ただし距離だけの寄与は分けられない（Cloud の実行場所を変える案 D-10 をしていない）

H3st.rerun による二重実行仕組みは確認済み。対策（D-09）をしていないので、再実行2回の構造は残っている（推定）

調べるうちに、仮説になかった候補も出てきました。サイドバーの固定往復（C1）、N+1（C5）、表示時の書込み（C6）、そしてStreamlit 側の実行・描画の時間（C8）です。C8 は、改修後も「残っている可能性がある」としか言えません（改修後の時間は、往復数ではほぼ説明できませんでした）。

本番 DB に対する時間の計測は、途中で打ち切りました（人間の判断）。そのため、DB 側の処理時間とネットワークの時間は分けられていません。

4

実装: 3つの考え方（D-06 / D-08 / D-07）

PM が採用したのは、往復の回数を減らす3つの方式です。どれも「1回の電話を速くする」のではなく、「電話の回数を減らす」考え方です。

D-06: サイドバーの値を持ち続ける

未読件数や権限を、画面を切り替えるたびに聞き直すのをやめ、session_state に保持します。聞き直すのは、通知・メッセージ画面を開いたときと、既読にした直後だけです。

効くところ: 全画面の遷移（サイドバーは毎回あるため）。

D-08: まとめて取得する（N+1 をなくす）

「部活1つにつき1回」と聞く代わりに、「必要な部活の分を1回でまとめてください」と聞きます。部活が10個でも100個でも、電話の回数は同じになります。

効くところ: ホーム、人を探す、部活の管理、メッセージ、部活詳細、プロフィールの6画面。

D-07: 読んだ結果を短い間おぼえておく（キャッシュ）

st.cache_data で、読取の結果を保存し、同じ内容をもう一度聞かないようにします。申込・書込みのあとは、関係するキャッシュをすぐ捨てます（古い表示が出ないようにするため）。

鮮度のルール: 「更新の直後だけ取り直す」（PM 決定）。一定時間ごとに更新する方式は採りませんでした。他の人の操作が原因の古さだけは、許容します。

採らなかった案

  • D-09（画面遷移の再実行を2回から1回にする）: 追加の調査は行わず、未採用。
  • D-10（Cloud か Supabase の場所を近づける）: 運営への相談が必要なため見送り。

実装の進め方

AI（terao）が実装し、テスト（kurosu）を付け、人間が PR をレビューしてマージしました。順番は D-06（PR #169）→ D-08（画面ごと、#170〜#177）→ D-07（#178）です。

結果: 7遷移は目標内、4遷移は時間未達

確認できたこと: 往復の上限（S-64）は合格（24行すべて上限以内）。時間は、代表11遷移のうち合格7・不合格4。改修前より遅くなった遷移は0。

判定の規則（通称「甲」）は、各遷移を2回測り、2回の平均が 1.0 秒以内、かつ大きいほうが 2.0 秒以内なら合格です。単位は ms（平均）。出典は 16-before-after.md です。

鮮度のテスト（S-65）

キャッシュを入れたあと、申込・キャンセルの直後に、部活詳細・自分の申込・未読件数が古いままにならないことを確かめるテスト12件が合格しました（ただし偽データのアプリでの確認です）。

この結果の限界（未確認）

  • 時間を測ったのは代表遷移のみで、各2回です。測っていない遷移（④の未読あり、⑨⑪⑬、検索入力、幹事の③⑭など）は未測定です。
  • 往復の上限はちょうどで余裕0のセルが多いです。あとで1往復でも増えると超過します。
  • D-07（キャッシュ）は偽データのアプリでのみ検証しています。実際の Cloud での命中率は未測定です。
  • 実データベースでの「まとめて取得」の書き方（埋め込み select）は、全般には確認していません。
  • 開催の絞り込みをせず全件を取得して判定している箇所があり、転送量は実測していません。
  • キャッシュのため、開始時刻を過ぎても「申し込む」ボタンが残ることがあります（押すと「申込できません」と出て、申込は作られません）。
  • ホーム・部活を探すの鮮度テストは、検出力が弱い（キャッシュの捨て忘れをしても落ちない）ことが分かっています。
  • 測定したデプロイ版は連絡で知った版で、Cloud の画面では確認していません。測定の一部に、間隔の短い連続クリックが含まれた疑いがあります。
6

企画・実行で学んだこと

① 最初の基準は厳密だったが、測ってみて現実に合わせて見直した

最初に5つの文書（要求・要件・仕様・設計・テスト設計）を、厳密に作りました。ところが、実際に測ってみると、決めておいた基準が現実に合わない場面が出ました。そこで、途中で人間（PM）が確認しながら次のように見直しました。

見直したもの最初見直し後
判定の規則中央値・最大で判定（各5回）「甲」: 2回の平均が1.0秒以内、かつ大きいほうが2.0秒以内
往復の上限全遷移で3回（案）キャッシュなしの初回の値で、遷移ごと・社員の種類ごとの上限（のち2か所を緩めた: ⑦ 6→7、⑭ 一般6→7・運営者4→5）
計測の回数各5回各2回

計測を各5回から各2回にした理由は、チームの記録（god のメモ）に「トークン削減のため」と書かれています。ただし、PM 本人の言葉での説明は文書に残っていません。

ここから学べること: 最初に厳密に作っても、測ると基準が現実に合わないことがあります。そのときは、基準を黙って変えず、「何を・なぜ・誰が」変えたかを記録します。数字を満たさなくなったからと基準を緩めるのではなく、決める人（PM）が判断し、記録に残します。

② Streamlit Community Cloud は、main への反映で自動デプロイされる

  • ファイルを保存しても、commit しても、公開アプリには反映されません。
  • PR を作っただけでも、原則として反映されません。main に push／マージすると、自動でデプロイされます。
  • だから、間違ったコードをマージすると、公開中のアプリに直結します。開発用の環境を分けて、マージの前に確かめる必要があります。
  • どのブランチを見て自動デプロイしているかは、Cloud の Settings で確認できます。今回は画面で確認していないため、断定しません。

③ トークン（AI の作業量）を抑える工夫

時間の計測は、画面の画像を撮らず、ブラウザの JavaScript で時間を文字で取得する方式にしました。約30回ごとに会話を区切りました。ほかに、5つの文書の見直し、計測回数の削減（5回→2回）、評価基準の見直しも、作業量を抑える方向に働きました。定例の報告は1〜2行にし、PR はテンプレートにしました。

注意: 作業量を抑えるために、測定の信頼性は下がります（各2回では、1回の外れ値が結果を大きく動かす）。何を減らしたかを、結果と一緒に書いておくのが大切です。

④ Manage app の使い方

Streamlit Community Cloud の「Manage app」から、アプリを操作できます。今回使ったのは次のとおりです。

  • Reboot app: アプリを再起動します。今回、プロフィール画面のエラーが、これで解消しました（7章）。
  • ログ: エラーの本文を確認する場所です。今回は、アプリの管理者経由でログをもらうと2〜3日かかる見込みだったので、待たずに、画面側でエラーの原因を絞れる診断表示を一時的に入れました（のち削除。PR #185）。
7

初心者が覚えておくこと・エラー集

自分の画面が遅いとき、原因を調べる手順

  1. 遅い操作を1つに決める。「あのボタンを押して、あの画面が出るまで」と、起点と終点を言葉にします。
  2. 往復を数える。偽データのアプリで、その操作が何回データベースに問い合わせるか数えます（このプロジェクトでは tests/count_profile.py。2回目以降の数は --warm）。
  3. 数が多い理由を探す。「サイドバーが毎回聞いている」「件数に比例して増える（N+1）」「同じ内容を何度も聞いている」のどれかを疑います。
  4. 直す前に、時間も測る。Cloud で、画面を前面にして、起動済みの状態で、同じ操作を複数回測ります。
  5. 直して、同じ方法で数え直す。数が減ったか、時間が減ったかを、直す前の記録と並べます。
  6. 残ったものは「残った」と書く。原因が分からないときは、「推定」「未確認」と書き分けます。

測るときの落とし穴

  • 画面が他のウィンドウに隠れると、ブラウザのタブが hidden になり、時間が大きく出ます。計測中は画面を前面に出します。
  • 連打すると、2回目が速く出ることがあります。1操作ずつ、間を空けて測ります。
  • 1回目と2回目は別物です（初回は遅いことがある）。何回目を採用するかを先に決めます。
  • 偽データのアプリで通っても、Cloud（本物のデータベース）で動くとは限りません（下のエラー集）。
  • テストが、実際の時刻に依存して、日が変わると落ちることがありました。時刻は固定して試します。

エラー集

AttributeError（プロフィール画面だけ、Cloud で落ちる）
起きたこと: 偽データのアプリでは通るのに、Cloud では⑤（自分のプロフィール）、⑩（主催者プロフィール）などでエラー画面になった。画面には「The original error message is redacted…」と出る（原因は秘匿表示）。
対処: データベースからの戻りの形（dict・list・None のどれか）が偽データと違う、という見立てで、戻りの形をそろえる処理（正規化）を入れた（PR #181）。
学び: 偽データで通ったテストは、実データベースの戻りの形までは保証しません。
httpx.RemoteProtocolError（人を探す→プロフィールで出た）
起きたこと: クリック後も見出しが変わらず、この名前のエラーが出た。
原因: AttributeError と同じ原因かは未確認。接続の使い回しによる切断の可能性が挙がったが、確認していない。
マージしたのに、直っていない（古いプロセスが残る）
起きたこと: 修正を main にマージして Cloud が更新されたのに、プロフィール画面のエラーが再現した。Cloud のデプロイのログは「Pulling → Updated app!」だけで、再起動の記録がなかった。
対処: Manage app の Reboot app で解消した。古いプログラムが動き続けていた疑いがある。
未了: 修正の効果と Reboot の効果は、切り分けられていません。
学び: マージのあと挙動が変わらないときは、古いプロセスを疑い、Reboot を試す。測定の最中は、アプリの変更を入れない（測定の前提が変わるため）。

初心者が覚えておく5つのこと

  • 画面が遅いときは、まず問い合わせの回数（往復）を数える。
  • 直す前に目標を数字で決め、直す前の値を記録する。
  • まとめて取得（D-08）・保持（D-06）・キャッシュ（D-07）は、回数を減らす道具。キャッシュは、書込みのあとに捨てる設計とセットで使う。
  • 偽データで通っても、Cloud で確かめる。マージ後は Reboot が要ることがある。
  • 推定は推定、未確認は未確認と書く。成功を盛らない。

別件（性能改善とは別に残っている課題）: プロフィールを画面の下のほうから開くと、新しい画面も下の位置のままで、名前が見えないことがあります（スクロール位置が先頭に戻らない）。ユーザーからの指摘（2026-10-16）で、原因・再現手順は未確認、別カード候補（未起票）です。
