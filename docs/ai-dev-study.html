この会のゴール: 部活コンシェルジュの企画 → 実装 → テストまでの一連の流れで学んだことを共有し、次の STEP3 のグループワークで活かしてもらう。

①

AI駆動開発のキーポイント ―「確率」を仕組みでコントロールする

正しく進む確率を、仕組みで上げる。これがこの資料の背骨です。

例1 .md ファイルで出力を制御する

役割・話し方・やってよいこと／いけないことを .md に書いて、毎回読ませます。たとえば「文書に書いていないことは作らず、『仕様に書かれていません』と報告して止まる」というルールです。ぶれ幅そのものを狭めます。

例2 複数のエージェントでレビューする

1体が書き、別の1体が確かめます。2体とも同じところを見落としたときだけ、ミスが残ります。2体で見ることで、正しい成果物が残る確率が上がります。

書く役（yamapi）▶ 検証する役（kurosu）▶ 人がレビュー▶ 公開

実例: テストのナレッジページ（テストの企画から実行まで）では、yamapi の下書きを kurosu が事実確認しました。結果は必須の修正2件・推奨3件・任意2件で、必須の2件を直してから公開に回しました（2026-10-16、統括の記録）。

注意: 同じモデル・同じ前提で見ると、ミスが重なることがあります。今回効いたのは、「書く役」と「検証する役」を分け、検証する役に元の記録を見に行かせたことです。

最初の仕様書の質を大事にする

5文書（要求・要件・仕様・設計・テスト設計）をAIと作る前に、元になる資料の質を上げておくことが大事でした。特に重要なのは次の2つです。

  1. 課題設定と要求の具体化 ― 課題を深掘りして「本当に解くべき課題」を決め、それを解決するために「何を作りたいか」（要求）を言葉にする。
  2. 仕様のキー部分の具体化 ― どんなフローで動くか。フロントとバックの両方をイメージできるとよい。

今回は、はなえさんが要件定義書と開発仕様書で具体化してくれていたので、スムーズに進みました。

元の資料 → 5文書

要件定義書 v1.0 → v1.1はなえ作・9/23作成、9/27更新
目的・ユーザー・仮説・利用フロー
開発仕様書 v0.1はなえ作・9/27
構成・画面S01〜S10・データ
▶
5文書要求 R → 要件 F/N → 仕様 SP → 設計 ＋ テスト設計

キー部分の例: 「部活を探す」フロー（要件定義書 v1.1 7章A）

条件で検索▶ カード一覧▶ 部活詳細（開催一覧・参加者）▶ 開催を選んで申込▶ DBに保存・幹事にアプリ内通知▶ 申込完了画面▶ メッセージで幹事とやり取り

画面の流れ（フロント）の途中に、「DBに保存・幹事に通知」（バック）が1行で入っています。開発仕様書 v0.1 には、画面の一覧（S01〜S10）と、データの表（社員・部活・開催・申込・メッセージ・通知など）まで書かれていました。

資料は 02_プロジェクト/bukatsu_concierge/inputs/ にあります（リポジトリには含めていないため、リンクはありません）。5文書は 要求.md から辿れます。

Issue の具体化（before / after）

after（上半分）

「💬 これは何？」「✅ 完成すると何ができる？」。初心者向けに書き足した部分です。何を作るのか、できあがると何ができるのかを、普通の言葉で書いています。

before（下半分）

「対応: SP-53〜SP-57」「受入基準」「触るファイル」。元の書き方です。記号と番号が中心で、文書を開かないと中身が分かりません。

進捗管理ダッシュボードの自動化

前提: GitHub Pages とは

GitHub のリポジトリに置いた HTML を、そのまま Web ページとして公開できる機能です。公開リポジトリなら無料プラン（GitHub Free）で使えます。非公開リポジトリで使うには、有料プラン（GitHub Pro・GitHub Team など）が必要です。

使い方の流れ

1. 見せたい内容を決める▶ 2. AI に指示して HTML を1枚作る▶ 3. docs/ に置いて push▶ 4. GitHub Pages で公開される

この案件では、dashboard.yml が main への push のたびに自動で公開しています。

出典: GitHub 公式ドキュメント「GitHub のプラン」

狙い

開発段階ごと・人ごとに、進捗を見える化すること。PR本文に Closes #番号 と書いてマージすると、Issue が自動でクローズされます。これで、進捗管理の手間をゼロにしました。

PR本文に Closes #12▶ マージ▶ Issue が自動クローズ▶ ダッシュボードを再生成

つまずいたこと

開発中に仕様の不備・抜け漏れが見つかり、I/F契約を直しました。ところが、そこで増えたタスクを「いつ・誰が Issue にするか」のルールがなく、Issue の外で進みました。その結果、ダッシュボードに表れず、Issue 側から後で追えませんでした（PR には残っているので、後追いはできます）。

テストは準備が大事

AIに任せたこと：テスト文書の作成 → テストフローの設計 → 実行 → 証拠ログの記録

1. 先に5文書のミスを直す

実装と文書のずれ、更新漏れを、テストの前に直します。

実例: 2026-10-10 のテストレビューで、仕様と実装のずれが34項目見つかりました。原因は、9/27 の初回提出の後、文書の更新（v0.2）が漏れていたことでした（統括の記録）。

2. テスト実行手順書で工程を見える化

何を、誰が、どうテストするかを1つの手順書にまとめます。分担するときに特に大事です。

詳しくは テストの企画から実行まで にあります。

この章で上げた確率テストが正しく機能する確率

次の開発でチャレンジしたいこと

テーマ今回の反省次にやること
1仕様のビジュアル化仕様を変えたとき、何が変わったのかをつかめなかった。.md だと構造が見えにくい主要フロー図を軸に、画面遷移図・ER図を添える。変更前後を並べて色を付ける
2Issue 設計の具体化何を作るか・完了条件が伝わらなかった。増えたタスクを Issue にするルールもなかった誰でも分かる言葉で書く。完了条件は、AI が合否を判断できる形（何をどう確かめれば完了か）まで具体化する。仕様変更で増えたタスクは「いつ・誰が」Issue にするか決めておく
3裁量とルールの明確化裁量があいまいで、工夫する余地も迷わず進むルールもなかった「自分で決めてよいこと／確認が要ること」を最初に決める（例：デザインの変更は担当者が判断、I/F契約の変更はPMに確認。ベーさんのルールがお手本）
4PR レビューの自動化コードレビューが PM のはなえさん1人に集中した。重要度や変更の大小を分けず、すべて同じようにレビューを依頼していたClaude が1時間に1回 PR をレビューし、マージまで判断する。人は重要度の高い変更だけを見る。前提は 2 の完了条件
5.md のアップデート用意された仕組み（.md）を、自分たちの開発に合わせてカスタマイズして使いこなせなかった。週1回の自動ナレッジ化も、自動で起動せず機能しなかったまず「どの確率を制御したいか」を決め、班の開発に合った仕組みに .md を育てて機能させ、開発の精度・クオリティを上げる

主要フロー図を軸にする理由: 今回の I/F契約の修正のように「処理の順番」が変わる場面が、最も分かりにくかったため。

裁量とルールの関連: 確定前に発注した画面を AI が先に作り、作り直した（実践ナレッジ 5.4）。
