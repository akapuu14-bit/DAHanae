AI駆動開発のキーポイント ―「確率」を仕組みでコントロールする

AIの出力は毎回少しずつ違い、ときどき間違えます。これは普段のAI利用と同じです。だから「1回で正しく出させる」ことより、間違いが残る確率を仕組みで下げることを考えました。この考え方が、この資料全体の背骨です。

例1 .md ファイルで出力を制御する

役割・話し方・やってよいこと／いけないことを .md に書いて、毎回読ませます。たとえば「文書に書いていないことは作らず、『仕様に書かれていません』と報告して止まる」というルールです。ぶれ幅そのものを狭めます。

例2 複数のエージェントでレビューする

1体が書き、別の1体が確かめます。2体とも同じところを見落としたときだけ、ミスが残ります。2回続けてミスする確率は、1回ミスする確率より下がります。

書く役（yamapi）▶ 検証する役（kurosu）▶ 人がレビュー▶ 公開

実例: テストのナレッジページ（テストの企画から実行まで）では、yamapi の下書きを kurosu が事実確認しました。結果は必須の修正2件・推奨3件・任意2件で、必須の2件を直してから公開に回しました（2026-10-16、統括の記録）。

注意: 同じモデル・同じ前提で見ると、ミスが重なることがあります。今回効いたのは、「書く役」と「検証する役」を分け、検証する役に元の記録を見に行かせたことです。

最初の仕様書の質を大事にする

5文書（要求・要件・仕様・設計・テスト設計）をAIと作る前に、元になる資料の質を上げておくことが大事でした。特に重要なのは次の2つです。

  1. 解決したい課題と要求の具体化 ― 誰が、何に困っていて、どうなれば嬉しいか。
  2. 仕様のキー部分の具体化 ― どんなフローで動くか。フロントとバックの両方をイメージできるとよい。

今回は、はなえさんが要件定義書と開発仕様書で具体化してくれていたので、スムーズに進みました。

キー部分の例: 「部活を探す」フロー（要件定義書 v1.1 7章A）

進捗管理ダッシュボードの自動化

前提: GitHub Pages の作り方

docs/ の HTML▶ dashboard.yml が site/ にコピー＋ダッシュボードを生成▶ GitHub Pages で公開

main への push で自動的に動きます。Issue・PR の状態が変わるたびにも、ダッシュボードを作り直します。

小話

  • 新しいページを足したのに、コピー一覧に入れ忘れて、本番だけ404になった（実践ナレッジ 5.11）。
  • PR の上では公開ジョブが毎回失敗し、main では成功した（同 5.12）。統括の記録（2026-10-16）では、環境の保護ルールによるもので想定内とされています。

狙い

開発段階ごと・人ごとに、進捗を見える化すること。PR本文に Closes #番号 と書いてマージすると、Issue が自動でクローズされます。これで、進捗管理の手間をゼロにしました。

PR本文に Closes #12▶ マージ▶ Issue が自動クローズ▶ ダッシュボードを再生成

苦戦したこと

開発中に仕様の不備や抜け漏れが見つかり、I/F契約を修正しました。その修正で増えたタスクは Issue 管理の外になり、Issue 側では後から追えませんでした。PR の記録には残っているので、後追いはできます。

実例: 画面が呼ぶ関数が I/F契約に無く、契約に足す PR（#90・#91）を出した（実践ナレッジ 5.8）。契約の文言の修正が先のマージに間に合わず、別の PR（#79）で直した（同 5.9）。

テストは準備が大事

自動化したもの: AI によるテストの実行と、証拠ログの記録。

1. 先に5文書のミスを直す

実装と文書のずれ、更新漏れを、テストの前に直します。

実例: 2026-10-10 のテストレビューで、仕様と実装のずれが34項目見つかりました。原因は、9/27 の初回提出の後、文書の更新（v0.2）が漏れていたことでした（統括の記録）。

次の開発でチャレンジしたいこと

1. Issue 設計の具体化

実装しやすく、完了条件がはっきりした Issue にする（③の苦戦から）。

2. PR レビューの自動化

完了条件がはっきりしていれば、1時間に1回の自動レビューで「手動で見るか、自動でよいか」を判断できるはずです。

裏付け: 課題 #43・#44 は、完了条件を「合否と実行ログが記録されること」と決めていたので閉じられた（実践ナレッジ 5.18）。

3. メンバーが判断できる柔軟性と、ルールの明確化

ベーさんのルール設定がステキでした。担当者の裁量・やっていいこと・やってはいけないことが具体化されていました。PM の確認が要ること／確認なしで進めてよいことを、同じようにルールにしたいです。

区分例
担当者の裁量（自分で判断してよい）デザインの変更
PM の確認が要る（確認なしで進めない）I/F契約の変更

関連: 確定前に発注した画面を AI が先に作り、作り直した（実践ナレッジ 5.4）。

4. .md ファイルのアップデート

これまでの開発のエラー・ミスを、週1回自動でナレッジにする設計にしましたが、うまく機能しませんでした。中身の理解を高めて改善したいです。

自動で起動していなかった事例: クラウドの定期実行（Routine）を、cron 0 18 * * 0・過去7日の失敗を抜き出して PR にする設定で用意しました。発火した実績は確認できていません（リモートに該当ブランチが無い）。2026-10-15 に、だーあさの判断でナレッジ還元は手動運用に切り替えました（01_ナレッジ/log.md）。原因は特定していません。記録上は「月曜18:00 JST」ですが、cron の 0 18 * * 0 を UTC で読むと月曜03:00 JST になり、食い違いがあります。
