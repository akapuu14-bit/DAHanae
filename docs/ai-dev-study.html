全体像 ― 5工程と、AI・人の分担

今回の取り組みは、次の5工程です。それぞれで「AIが担当したこと」と「人が決めたこと」を分けて重ねました。

AIの担当人が決めた点

① 5文書の作成

AI資料3種から要求を抽出、要件・仕様の案、資料間の食い違いの検出
人保留24項目の裁定、対象版と実装開始の承認

② Issueの具体化

AI仕様IDからタスクに分解、受入基準・触るファイル・実装のコツを記入
人担当の割り当て、方針（実装は人が各自）

③ GitHubの管理

AILabel・Milestone・Issueの一括作成スクリプト
人PRのレビューとマージ、Pages有効化（オーナー権限）

④ 進捗管理

AIダッシュボードの生成と自動更新の仕組み
人PRに Closes # を書く、公開範囲の判断

⑤ テスト実行計画

AIテスト設計、テストの実行と証拠ログの保存

基本の流れは 提案 → 確認 → GO → 実装 → レビュー → 反映 です。人が決める箇所は必ず「提案」として出し、本人の回答を記録してから進めました（実践ナレッジ 1章）。

実装はAIではなく人が各自で行う方針に、途中で変えています。AIが書いたコードが衝突したためです（実践ナレッジ 5.5）。

実例
  • 要求: 企画書・要件定義書v1.1・開発仕様書v0.1 の3資料から抽出。資料間でMVPスコープが食い違うことをAIが見つけ、人へ上申した。
  • 要件: 保留24項目を表にして、人が裁定した。
  • テスト設計を書く途中で、kurosuが仕様の穴を5件見つけ、4件を仕様に反映した。
  • 対象版 9a6a20f と実装計画に、PMが承認（2026-09-27）。承認の記録がない会話だけでは実装を始めない決まり。

リンク: 要求.md ／ 要件.md ／ 仕様.md ／ 実装計画.md（5章 承認欄）

「書いていないことは作らせない」

スタッフAIは文書にあることだけを作り、書いていないことは「仕様に書かれていません」と報告して止まります（V字フロー規定のゲート）。実装中に、画面が呼ぶ関数がI/F契約に無いと分かったこともあります（あかぷが発見）。その場で補わず、「仕様外の補完」ではなく「契約の穴埋め」と判断して、契約に関数を足すPR（#90・#91）を出してから進めました（実践ナレッジ 5.8）。逆に、確定前に発注した画面をAIが先に作ってしまい、作り直したこともあります（同 5.4）。

学び
文書を先に固めると「何が未決か」が表になり、人の判断が速くなる。

GitHubの管理

以前（風船アプリ）
【要確認：ユーザー記入】
今回
AIがスクリプトで Label・Milestone・Issue を作成▶ ブランチで作業 → PR▶ 人がレビュー・マージ
作ったもの中身
Labelarea（be/ui/pdm）・type（feature/bug）・prio（high/mid/low）の8つ＋ wave:0〜4
Milestone「〜9/29 アプリのカタチ」「〜10/2 8割」「10/7-12 最終」の3つ

スクリプトは、すでにあるLabel・Milestoneは作らずに飛ばすので、何度流しても重複しません。PRのマージは人が判断し、自分のコードを自分で承認しない形にしました（実装計画 1章）。

実例
  • ローカルの main から分岐して、関係ないコミットがPRに混ざった → 基準を常に origin/main にした（実践ナレッジ 5.10）。
  • 作業フォルダの状態のせいで、1ファイルの修正が116ファイルの「削除」を巻き込んだ。レビューで見つけて復元し、git の安全ルールを作った（同 5.16）。
  • 新しいページを足したのに、公開のコピー一覧に入れ忘れて404になった（同 5.11）。

リンク: scripts/setup_github.sh ／ github-管理セットアップ.md

学び
作るのはAIに任せ、main に入れる判断は人が持つ。マージ前の差分確認が最後の砦になった。

今回
PR本文に Closes #12▶ マージ▶ Issueが自動でクローズ▶ ワークフローが集計▶ ダッシュボードを更新・公開

集計は、Issue・PRの変化、main への push、毎日1回の定時、手動のいずれでも動きます。人が手で行うのは「Issueを立てる」「PRに Closes # を書く」の2つだけです（進捗管理ガイド 4章）。

場所役割
ダッシュボード数字（誰が・どれだけ・遅れているか）。自動更新
overview地図（全体像と現在地）
タスクバックログ正本（受入基準・依存・所有境界）

UTC と JST のずれ

GitHub Actions の時刻は UTC です。定時実行は「UTC 21:00 ＝ JST 06:00」と書いています。ダッシュボードでは、締切の判定は JST なのに、PRの時刻と生成時刻だけ UTC で表示されていました。PR #95 で表示を JST にそろえ、変換をテストで固定しました（実践ナレッジ 5.13）。

テスト実行計画

以前（風船アプリ）
【要確認：ユーザー記入】
今回
U 単体設計と対
部品を1つずつ
▶
I 結合仕様と対
部品をつないで
▶
S システム要件と対
全体を本物に近い形で
▶
A 受入要求と対
自己評価 → 他者評価

テストの1行は、上流の1つのIDに対応します。2章の糸では、F-10 → S-10 です。S-10 は 2026-10-11 に合格しましたが、記録には「偽のデータでの確認で、実DBの合格ではない」と書いてあります。

証拠の残し方

  • 合否は「合格／不合格／対象外／未実行」。空欄は未実行として扱う。
  • 合格にするのは、証拠（ログ・スクショ）のパスを書いてから。
  • どの方法で確かめたか（偽のデータ／実DBの読み取り／実機）を行ごとに書き分ける。
  • 直したあとの証拠は、全件を通しで取り直した1本にする。修正前と修正後の一部をつなぎ合わせない（実践ナレッジ 5.17）。
実例

「全件合格でないと閉じられない」という誤解

2026-10-12 時点で、結合テストは合格167／未実行37、システムテストは合格44／対象外2／未実行16でした。全件合格でないと課題を閉じられないのでは、という見方が出かけました。実際の受入基準は「合否と実行ログが記録・添付されること」でした。未実行を合格に数えず、残す理由を書いたうえで、#43・#44 を閉じました（実践ナレッジ 5.18）。

リンク: テストの企画から実行まで（詳しい流れと件数）／ テスト結果.md ／ #43 ・ #44

学び
閉じる条件は受入基準の文面で確かめる。未実行は合格と混ぜず、残す理由をその場で書く。

まとめ

以下は、1〜6章の記録から書記が整理したものです。

任せてよかったこと

  • 資料からの抽出と、資料間の食い違いの検出
  • 仕様IDからIssueへの分解と、本文の記入
  • Label・Milestone・Issueの一括作成
  • 進捗の集計とダッシュボードの更新
  • テストの実行と証拠ログの保存
  • 別の担当による横断レビュー（仕様の穴5件、Issueの二重化）

人が持つべきだったこと

  • 案の採否と保留の裁定（「Aで」「決定」）
  • 対象版を示したうえでの実装開始の承認
  • PRのレビューとマージ
  • 公開範囲の判断
  • テストで何を合格とするかの指定と、課題を閉じる判断

失敗の多くは「確認前に動いた」「境界が書かれていなかった」「書式がそろっていなかった」のどれかでした。この3つを先に潰すと、AIに任せられる範囲が広がります。
