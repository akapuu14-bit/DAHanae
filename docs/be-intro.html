4 層の絵

このアプリは、仕事を 4 つの層に分けて作っています。ユーザーの操作は上から下へ流れ、結果は下から上へ戻ります。

画面（screens）→ service → repository → データベース（Supabase）
層やることやらないこと
画面表示と入力の受け取り。うまくいかなかったときに、例外の種類を見て文言を出すデータベースに直接さわらない（画面が使うのは service と、その例外 services.errors まで）
service仕様書のルールに沿って、できるか・どの順で行うかを決める画面の文言を作らない。SQL を書かない
repositoryテーブル 1 つにつき 1 ファイルで、データベースの読み書きだけをする業務のルールを持たない
データベースデータを保存する。型や制約で、不正な値を最後に止める—

迷ったときの振り分け方は 3 つです。

  • 画面の見た目に関わる → 画面
  • 「できるか」「どの順か」というルール → service
  • テーブル 1 枚の読み書き → repository

出典: BE実装チートシート「開発の全体像」「1 導入: 層構成と『層の責務』」。

2 ／ 目安 10 分

ログインの流れ 1 本

社員 ID とパスワードを入力してから、ログインできる／できないが画面に出るまでを、4 層を通して追います。

  1. 画面（screens/login.py）が、社員 ID とパスワードの入力を受け取る。
  2. 画面は、本人かどうかの判断を自分ではせず、service（auth_service.login）に頼む。
  3. service は repository（employees_repo.get_by_id）に「この ID の社員を出して」と頼む。
  4. repository がデータベース（Supabase）から社員を 1 件取り出して返す。見つからなければ None。
  5. service が、ID が見つかったか・パスワードが合っているかを判断する。ダメなら例外（AuthenticationError）を投げ、よければ社員のデータを返す。
  6. 画面が結果を見る。例外なら失敗の文言を出し、成功ならログイン状態にして画面を切り替える。

service のコード（歩 2〜5）

def login(employee_id: str, password: str) -> dict:
    employee = employees_repo.get_by_id(_normalize_id(employee_id))
    expected = str(st.secrets["common_password"])
    password_ok = hmac.compare_digest(
        (password or "").encode("utf-8"), expected.encode("utf-8")
    )
    if employee is None or not password_ok:
        raise AuthenticationError()
    return employee

読み方の目安（細部は読めなくてよい）:

  • 1 行目: 入力された ID を整えて（前後の空白を除き、大文字にそろえて）、repository に社員を探してもらう。
  • 2 行目: 正しいパスワードは、コードに書かず st.secrets（秘密の置き場）から読む。
  • 3〜5 行目: パスワードを照合する。比べるのに == ではなく専用の関数（hmac.compare_digest）を使うのは、比べる時間から中身を推測されないため。
  • 6〜7 行目: 社員が見つからない、またはパスワードが違うなら、同じ種類の例外を投げる。どちらが違うかは区別しない（教えないため。仕様 SP-11）。
  • 8 行目: 成功なら社員のデータ（dict）を返す。

画面のコード（歩 1・6）

if submitted:
    try:
        employee = auth_service.login(employee_id, password)
    except AuthenticationError:
        st.error(ERROR_MESSAGE)  # SP-11
    else:
        state.login(employee["id"], employee)
        st.rerun()
  • try の中で service を呼ぶ。except AuthenticationError は「その例外が投げられたら」。失敗の文言（ERROR_MESSAGE）は画面が持っている。
  • service は日本語の文言を持たない。「何が起きたか」を例外の種類で伝え、「どう見せるか」は画面が決める。
  • ここで受けているのは AuthenticationError だけ。ほかの例外はこの画面では受けていない。

出典: BE実装チートシート「開発の全体像」の「例: ログインの流れ」、5.1。コードは app/frontend/services/auth_service.py・app/frontend/screens/login.py（origin/main 07176e8）。

repository と service の役割の違い

同じ「開催への申込」を題材に、2 つの部品の違いを見ます。ひとことで言うと、repository は「データがあるか・取り出す・書き込む」、service は「それでよいか・どの順でやるか」を決める部品です。

repository: 「同じ開催に申込済みの申込があるか」を調べるだけ

def exists_active(event_id: int, applicant_id: str) -> bool:
    res = (
        supabase.table("applications")
        .select("id")
        .eq("event_id", event_id)
        .eq("applicant_id", applicant_id)
        .eq("status", "申込済み")
        .limit(1)
        .execute()
    )
    return bool(res.data)

申込（applications）のテーブルに、この開催・この人・状態が「申込済み」の行があるかを調べ、あれば True、なければ False を返します。「あったらどうするか」は決めません。

service: 「あったら申し込めない」と決める

if applications_repo.exists_active(event_id, applicant_id):
    raise ConflictError("already_applied")

repository の答えを受けて、「すでに申込済みなら、この申込は成り立たない」というルールを持つのが service です。ルールを破るので、例外 ConflictError を投げ、理由（"already_applied"）を添えます。画面はこの理由を見て、仕様どおりの文言を出し分けます。

順序も service の仕事

申込の処理は、service が次の順に進めます。

  1. 確認する（開催はあるか、重複していないか）。ダメなら何も保存せず、例外を投げる。
  2. 保存する（申込を 1 件追加する）。
  3. 保存したあとの付随の処理をする（幹事への通知、操作の記録）。

失敗するなら、何も保存する前に失敗させる。通知や記録は「申込が保存された」ことを前提にするので、保存のあとにやる。こうした「順序」も repository ではなく service が持ちます。

「見つからない」の返し方

repository は、探したものが無いときに例外を投げません。返し方は関数によって、None（「何も無い」を表す Python の値）、空のリスト []、False、0 のどれかです。たとえば get_by_id は社員が見つかれば dict、無ければ None を返し、exists_active は True / False を返します。

「見つからない」ことをエラーにするかは、使う側の service が決めます。たとえば auth_service.get_role は、指定された部活が無いと NotFoundError を投げます。

なお repository 自身は、二重申込を防ぐ独立した仕組みを持ちません。最後の砦はデータベース側の制約（申込済みの申込を 1 人 1 件に絞る部分一意インデックス applications_one_active_per_employee_idx）です。

まとめ: repository = データベースの出し入れ（ルールを持たない）。service = ルールと順序を決め、うまくいかないとき例外で知らせる。画面 = 例外を見て文言を出す。

出典: BE実装チートシート 1 章、3.2、5.2、5.3。コードは applications_repo.py・application_service.py・errors.py（origin/main 07176e8）。

用語 10 個

これまでの節で出てきた順に並べました。詳しい説明は 実装ガイド/用語集.md と、BE実装チートシートの「前提用語ミニ辞典」にあります。

1. 画面（screens）
ユーザーが見る部分。表示と入力の受け取りをする。うまくいかなかったときの文言は、ここで出す。
2. service（サービス）
「申込できるか判定する」「未読件数を数える」のように、仕様書の業務ルールを実行する部品。repository を呼び、結果を画面に返す。エラーの文章は作らない。
3. repository（リポジトリ）
テーブル 1 つにつき 1 ファイルで、データベースの読み書きだけを担当する部品。業務のルールは持たない。
4. データベース／Supabase
データを保存する場所。このアプリは、チームで 1 つの Supabase（PostgreSQL をクラウドで使えるサービス）を共有している。
5. dict（辞書）
Python の「キーと値の組」。1 件のデータ（たとえば 1 人の社員）を {"id": "E001", "name": "…"} のように持つ。repository の戻り値は、dict か dict のリスト。
6. 例外（Exception）
「うまくいかなかった」を知らせる Python の仕組み。raise で投げ、try/except で受ける。このアプリでは errors.py の例外だけを service が投げ、画面が種類を見て文言を出す。
7. 見つからないときの返し方（None など）
None は「何も無い」を表す Python の値。repository は、探したものが見つからないときに例外を投げず、None・空のリスト []・False・0 のどれかで返す（返し方は関数による）。エラーにするかは service が決める。
8. Secrets（st.secrets）
パスワードや鍵のような秘密の値の置き場。コードに直接書かない・コミットしない。コードからは st.secrets["common_password"] のように読む。
9. マイグレーション
データベースの構造（テーブルや制約）の変更を、SQL ファイルとして順番に残す方法。supabase/migrations/ にある。変更するときは既存のファイルを書き換えず、追加のファイルにする。
10. PostgREST／supabase-py
Supabase のデータベースを HTTP で操作する窓口が PostgREST。Python からは supabase-py で、次のようにメソッドをつなげて書く。SQL は直接書かない。
supabase.table("clubs").select("*").eq("id", 1)

意味は「clubs テーブルから、id が 1 の行を、全部の列で取り出す」です（3 節の exists_active も同じ書き方でした）。

理解確認の問い 5 問

1 問 1 分ほどで考えてから、答えを開いてください。答えは「一言でこう言える」という目安です。

問い 1

「画面」「service」「repository」のうち、try/except で例外を受けて、エラーの文言を出すのはどれですか。

答え

画面。service は、何が起きたかを例外の種類で伝えるだけで、文言は持たない（節 2）。

問い 2

社員 ID が存在しないときと、パスワードが違うときで、ログイン失敗の知らせ方が同じなのはなぜですか。

答え

どちらが違うかを教えないため（仕様 SP-11）。ID が存在するかどうかを、外から推測させない。

問い 3

st.secrets["common_password"] のように、パスワードをコードに直接書かないのはなぜですか。

答え

コードは共有・コミットされるため。秘密の値は、コードの外（Secrets）に置く（節 4 の用語 8）。

問い 4

「同じ開催に二重で申し込めない」というルールの判断は、repository と service のどちらが持ちますか。repository は何をしますか。

答え

判断は service（あったら ConflictError を投げる）。repository は、申込済みの行があるかを調べて True / False を返すだけ（節 3）。repository 自身は独立した重複防止を持たず、最後の砦はデータベースの部分一意インデックス（applications_one_active_per_employee_idx）。

問い 5

repository が「見つからない」ときに、例外を投げず None などで返すのはなぜだと思いますか。

答え

見つからないことは、異常とは限らない。repository はルールを持たず、「無かった」という事実を返す。エラーにするかどうか、エラーにしたときの文言は、service と画面が決める（節 2・節 3）。
