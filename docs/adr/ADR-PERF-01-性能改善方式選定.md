## 1. 起点（なぜ決めるのか）

発表で「Streamlit Cloudで全画面の遷移が遅い、検索も表示も」と指摘された（人間の報告。`0-feedback.md` §1）。要件N-01〜N-14に速度の要件はなく、文書の抜けだった。人間が目標値を案Aとして決めた（主要遷移の待ち時間が中央値1.0秒以内・最大2.0秒以内。Cloud・ウォーム・各5回。N-15）。あわせて、遷移1回のDB読取往復の上限を3回とする案があり（N-16）、本ADRと同じ2026-10-15のPMレビューで3回に確定した（4章）。

## 2. 確認した事実と推定（判断の前提）

## 3. 選択肢と比較

選択肢は、設計.md 5.7節の方針候補（D-06〜D-10）と、何もしない案。**組み合わせてもよい**（その場合は決定欄に組み合わせを書く）。往復の見込みは1Bの偽データ規模で、確度は「構造は確認済み・効果は推定」。時間の短縮量は実測の1往復時間が未計測のため数値にしていない。

| 案 | 内容 | 減るもの | 往復の見込み | 利点 | 懸念・未決 |
| --- | --- | --- | --- | --- | --- |
| 0 | 何もしない（現状維持） | なし | 部活を探す遷移8、ホームへの戻り18〜26 | 変更なし | N-15（中央値1.0秒以内）の達成見込みを示す材料が現状ではない。現状の参考実測は2069ms（n=1） |
| D-06 | サイドバー値（未読件数・権限）を`session_state`に保持 | 往復数 N | 遷移1回あたり最大6往復（運営者4）。8→2、18〜26→12〜20 | 全画面の遷移に効く。画面ごとの改修が小さい見込み | 未読件数の鮮度（どのタイミングで取り直すか）が未決。設計4章の`unread_count`の現行方針を変える |
| D-07 | `st.cache_data(ttl=…)`で読み取り結果を短時間保持 | 往復数 N | 画面・TTL・更新頻度に依存。未計測 | 読取の多い画面（ホーム、社員検索）に効く可能性 | 申込直後などで古い値を見せない無効化設計が要る。許容する古さは仕様に未記載 |
| D-08 | `in_()`・埋め込みselectで一括取得（N+1の解消） | 往復数 N | ホームは2C往復、社員検索はC+P往復の部分を定数化。画面ごとに再集計が必要 | データ量が増えても遅くならない | repo/serviceの形が変わる。I-F契約への影響を確認する必要 |
| D-09 | `state.go`の再実行を2回→1回に | 往復数 N | 遷移1回あたりサイドバー3往復 | 構造由来の無駄を省く | Streamlitの描画順の制約。実現可否は未検証 |
| D-10 | Cloudの実行リージョン、またはSupabaseの場所を近づける | 1往復の時間 t_q | 往復回数は変わらない | 距離が主因なら全画面に効く | 実リージョン未確認。Supabaseのリージョン変更は移行を伴い、運営への相談範囲（外部サービス・セキュリティの発展）に触れる可能性 |

比較の観点（決める人が使う）：①目標（N-15・N-16）に届く見込みの根拠 ②実装の大きさと既存契約への影響 ③データの鮮度（SP-70・SP-71、申込直後の表示）への影響 ④運営への相談が要るか ⑤改修後に同じ手順（SP-81）で再計測できるか。

## 4. 決定

| 項目 | 内容 |
| --- | --- |
| 決定日 | 2026-10-15 |
| 決定者 | PM（人間）。god が選択肢形式で質問し、各問の推奨案を明示したうえでの回答（PR #161 レビュー） |
| 採用する案（組み合わせ可） | **D-06 + D-07 + D-08**。D-09 は実現可否を先に調査し、採否は保留。D-10 は運営への相談が要るため、今回は見送り |
| 理由 | 3案はいずれも往復数 N を減らす方式で、全画面の遷移に効く見込みがある（D-06）、読み取りの重複を省ける（D-07）、件数に比例する往復を定数にできる（D-08）。根拠は本書3章の比較と `2-cause-analysis.md`。決定の根拠の記録は `evidence/perf/6-review-decisions.md` 【5】（回答は推奨どおり） |
| 捨てた案とその理由 | 「D-06 + D-08 のみ」「+D-09」「D-10も検討」は今回採らない。D-09 は実現可否が未検証のため調査してから判断する（見送りではなく保留）。D-10 は運営相談が要るため見送り。「何もしない」（案0）も採らない。個別の理由は回答の記録にこれ以上書かれていない |
| 鮮度の扱い（未読件数・申込直後）の決定 | 「更新の直後だけ取り直す」。未読件数は遷移中は保持値を使い、通知・メッセージ画面を開いた時と既読化直後に再取得する。申込・書込みのあとは関連キャッシュを即時に無効化する。古い表示は他者の操作が原因の場合のみ許容する。仕様は SP-84、要件は6章 #26。他の選択肢（一定時間で更新／キャッシュ不使用）は採らない。出典: `evidence/perf/6-review-decisions.md` 【4】 |
| N-16（往復上限3回）の確定可否・値 | **3回で確定**（5回にゆるめる／回数上限は置かない、は採らない）。根拠 1000ms÷約260ms≒3.8。要件6章 #25 は裁定済み。出典: `evidence/perf/6-review-decisions.md` 【1】。追記（2026-10-15、PM）：「部活の管理」画面のみ5回以内、他画面は誰が使っても3回（管理者の画面は別基準。根拠 5×約260ms≒1.3秒で最大2.0秒に収まる）。出典: `evidence/perf/7-plan-decisions.md` 【3】 |
| 撤退ライン（効果が出なかったときの見直し条件） | 決めていない（未記入）。改修後に SP-81 の手順で再計測し、N-15・N-16 を満たさなかった場合の扱いは、その時点で人間が決める |

関連する決定（方式の前提として同じレビューで決まったもの）：⑮管理画面タブ切替は時間を測らず「再実行なし・往復0」を1回確認する（主要遷移の時間計測は①〜⑭で確定。SP-79）。n<5 は判定不能にして測り直し、合否に使わず、破棄した回数と値を記録する（SP-81⑤）。出典: `evidence/perf/6-review-decisions.md` 【2】【3】。
