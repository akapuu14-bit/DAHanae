1

この記事で持ち帰ること

テストは「何を・いつ・誰が・どうやって確かめ、どう記録するか」を決めて回す一連の流れで、テスト設計はその流れの中の1枚です。流れが見えれば、自分の機能のテスト設計は書けます。

  • 2章: 要求からテスト・評価までの1枚の地図（これが主役）。
  • 3〜5章: 4種類のテスト（U・I・S・A）、準備、3つのテスト文書の役割。
  • 6〜8章: 実際に回した記録を例に、実行 → 確認 → その後の工程を辿る。
  • 9章: 実践の進め方（担当の割り振り、進捗の見せ方、完了条件）。
  • 10章: 場面別ガイド（もう1つの主役）。「いま何をするか」から引けます。

急ぐ人は、2章 → 10章だけ読めば足ります。詳しい元の文書へは、各章からリンク（ファイル名）で案内します。ここでは、重要なものに絞って説明します。

テストの全体の地図

この案件は「V字」で進めます（V字フロー規定.md）。左側で「作るもの」を決め、右側で、決めたことに対応する「確かめるテスト」を置きます。テスト設計は、左側の文書と対（つい）で書きます。

【決める（左）】                                【確かめる（右）】

 要求 ─────────────────────────────────────────▶ 受入テスト A  （使う人の目で、合格を決める）
   └ 要件 ───────────────────────────────────▶ システムテスト S（全体を本物に近い形で通す）
       └ 仕様 ─────────────────────────────▶ 結合テスト I  （部品をつないで確かめる）
           └ 設計 ───────────────────────▶ 単体テスト U  （部品を1つずつ確かめる）
               └ 実装（作る）

3

U・I・S・A とは

4種類のテストは、見る範囲の大きさが違います。日常のたとえで言うと、新しい自転車を作って、お客さんに渡すまでの確認です。

種類たとえ一言でいつ誰が実行何を見る（このアプリの例）
U 単体ブレーキだけを握って、きちんと効くか確かめる部品を1つずつ確かめる実装の直後（手順書上。この案件の実際の順序は6章）実装担当（手順書上）認証の部品が、大文字小文字の違うIDでも正しく動くか（services/auth_service.py）
I 結合ブレーキと車輪をつないで、握ると車輪が止まるか確かめる部品をつないで確かめるUのあとテスト担当仕様（SP）の分岐どおりに動くか。例: 同じ開催に重複申込できない（画面→処理→データ）
S システム完成した自転車で、本物の道を一周する全体を本物に近い形で通すIのあとテスト担当要件（F・N）を、画面をまたいで満たすか。例: ログイン → 申込 → キャンセル → 再申込
A 受入買う人が自分で乗って、「これで良い」と言う使う人の目で合格を決めるSのあとユーザー（判定）要求（R-11〜R-15）の主要な流れが、途切れず使えるか

つまずきやすい点: 「テストの設計」は左側の文書と対で書き、「実行」は下（U）から上（A）へ進みます。設計の向きと、回す向きは逆です。A の合否はユーザーだけが書きます（AI は代筆しません）。

出典: V字フロー規定.md「左右の対応」、テスト実行手順書.md 1章。ID の付き方は S-01、I-001、U-001、A-01（テスト設計.md・テスト結果.md）。

4

準備: 決めること・用意するもの

実行を始める前に、次を済ませます（テスト実行手順書.md 2〜3章）。準備のチェックリストとして使えます。

① 決めること

  • どの版を試すか: 対象のコミット ID を控える（git rev-parse --short HEAD）。
  • 誰が、どの種類を実行するか（3章の表）。実装した人と別の人が独立評価する。
  • 実行の順番（U → I → S → A。9章）。
  • 証拠をどこに置くか: evidence/test/ の U/・I/・S/・A/。

② 用意する文書

  • 要求.md・要件.md・仕様.md・設計.md（5文書。テストの根拠）
  • テスト設計.md（何を確かめるか。正本）
  • テスト実行手順書.md（どう回すか）
  • テスト結果.md（記録先。5章）

③ 環境とデータ

  • データは架空データだけ。実データを入れない。外部公開もしない。
  • ダミーデータは、まず python scripts/reset_data.py --dry-run で内容を確認する。--dry-run を付けずに実行すると、接続先 DB の全データが消える。実行前にチームへ声をかける。
  • 投入後の期待: 社員 500 名・部活 15 件（S-54）。seed は固定（S-55）。
  • 接続情報は各自の .streamlit/secrets.toml に置き、コミットしない。パスワードなど秘匿値は、記録・ログ・スクショのどこにも書かない。
  • 複数人が同じ DB を同時に操作すると結果がぶれる。誰がいつ実行するかを、先に知らせる。

④ 実行前の最終チェック

  • 対象のコミット ID を控えた。
  • ダミーデータ投入の日付・実行者を記録した。
  • 実 DB でログインできることを確認した。
  • 他の人がテスト中でないことを確認した。
  • 秘匿値が画面・ログに写らない設定になっている。
5

文書の役割: 3つの文書の違い

テストの文書は3つあります。中身の正本は1つだけで、他は「回し方」と「記録」です。食い違ったら、テスト設計が正です（手順書とテスト結果の側を直す）。

文書役割誰が使ういつ使う
テスト設計.md中身の正本。何を・どんな前提と操作で確かめ、どうなれば合格か（期待結果）設計する人、実行する人書く: 実装の前（上流の文書と対）／読む: 実行のたび
テスト実行手順書.md回し方。担当・実行順・環境準備・証拠の残し方・種類別の手順実行する人実行の前と、実行中
テスト結果.md記録。合否・実行日・実行者・証拠・備考（中身は写さない）実行した人（記入）、確認する人実行した同じ日に記入する

テスト設計の1行を読む（書き方の型）

自分の機能のテスト設計は、1行 ＝ 1つの確認で書きます。列は5つです。実際の行で見てみます（テスト設計.md より）。

列意味S-02 の例（システム）I-006 の例（結合・異常系）
IDテストの番号S-02I-006
対応元になる要件（F・N）／仕様（SP）F-02SP-06
前提試す前の状態（誰で・どんなデータ）一般社員でログイン／幹事または運営者でログインDB に接続できない状態
操作やることサイドバーを確認する画面を表示する
期待結果どうなれば合格か一般社員には「部活の管理」が表示されない。幹事・運営者には表示される「データを読み込めませんでした。時間をおいて再読み込みしてください」と表示される

自分の機能のテスト設計を書く手順（要約）:

  1. 機能の要件（F・N）を1件選ぶ → S を原則1ケース書く（画面をまたぐ確認）。
  2. その要件に対応する仕様（SP）の分岐を数える → I を分岐ごとに書く。
  3. 重要なもの（★: 重複申込防止、キャンセル・再申込、初参加判定、未読件数、非公開情報、権限、操作履歴の二重記録防止）は、正常系・異常系・境界値に分けて書く。
  4. 「前提・操作・期待結果」は、誰が読んでも同じ結果になる具体さで書く（上の例のとおり）。
  5. 仕様に書いていない挙動は、テストに足さない。「仕様に書かれていません」と報告し、末尾の「仕様との不一致・未定義」の章に挙げる。
6

実行フロー: この案件の U → I → S を1つずつ辿る

実際に回した記録（2026-10-10〜12）を例に、1段ずつ辿ります。実行の手順は テスト実行手順書.md 5章です。

U 単体（偽repo・実装担当）→ I 結合（テスト担当）→ S システム（テスト担当）→ A 受入（ユーザー）
 前段に不合格がある間は、それに依存する後段を「合格」にしない（原因が前段にあるため）

手順書上の順序と、この案件で実際に起きた順序は別です。上は手順書上の本来の運用です。この案件では、I は 2026-10-10〜11、S は 2026-10-11〜12 に実行・記録され、U の記録（U-001〜U-013）は、その後の 2026-10-12 に、実装担当とは別の実行者がまとめて行いました（テスト結果.md の実行日・実行者欄）。

「偽 repo」とは、データベースを使わない、本物そっくりの偽のデータ置き場（メモリ上のスタブ）です。速く何度でも試せますが、「実際のデータベースで動く」ことまでは言えません。

① 単体 U: 部品を1つずつ（実装担当）

  1. 対象の関数・モジュールを決め、テスト結果.md 4章に ID（U-001 から連番）と対象を書く。
  2. 偽 repo で呼び、期待どおりか確認する。
  3. 実行ログを evidence/test/U/ に保存し、合否・ログ・実行者を書く。

この案件の記録: 画面・配色の6組（U-001〜U-006）と、サービスの7組（U-007〜U-013）の計13組を、2026-10-12 に、実装担当とは別の実行者がまとめて実行・記録しました（対象コード 2da2eeb、ログ evidence/test/U/u-inventory-main-20261012.log）。ログの先頭に、対象コミット・実行者（実装担当ではない旨）・日時・環境・実行コマンドを書き、「実 DB は使っていない」ことも明記しています。

注意: U の合格は「偽 repo での部品確認」です。実データベースでの合格を意味しません。確認できた観点だけを記録し、対象のモジュールを全部網羅したとは扱いません。

② 結合 I: 部品をつないで（テスト担当）

  1. 実行前チェック（4章④）を済ませる。
  2. テスト設計の各行の前提を作る（データの状態・ログインする人）。
  3. 操作して、期待結果と照合する。画面の確認はスクショを撮る。
  4. ★付きは、正常系・異常系・境界値をすべて実行してから、その観点を「完了」とする。

この案件の記録: I は3つの方法で確かめました。

通称方法確かめられること確かめられないこと

L-C画面を自動操作（Streamlit の AppTest）＋偽 repo画面の表示・文言・遷移実 DB、ブラウザでの見た目
L-B実データベース（読取14行、書込3行）実 DB の検索条件・一意制約など画面（処理と DB の層のみ）

I の合格167件は、既存の L-A・L-C の合格150件＋L-B の実 DB 合格17件の合計です（テスト結果.md 7.3）。全167件が実 DB で合格した、という意味ではありません。

③ システム S: 全体を通す（テスト担当）

  1. 結合の主要な★が合格していることを確認する。
  2. テスト設計1章の各行を実行し、画面をまたいだ要件の充足を確認する。
  3. S-59 は設計上テスト対象外。N-01〜N-04・N-10 は実装レビューで扱う。

7

確認フロー: 合否判定・不合格の切り分け・記録

① 合否の判定（4語だけ）

語意味書ける条件
合格期待結果と実測が一致した証拠（ログ・スクショのパス、または PR／Issue のリンク）がある行にだけ
不合格一致しなかった証拠と、備考に「期待: …／実測: …」を書いてから。原因が分からなければ「原因未確認」と書く（推測で書かない）
対象外設計上、または承認された判断で、実行しない備考に理由と根拠を書く。実行できなかっただけなら、対象外にしない
未実行まだ実行していない（空欄も未実行）初期状態。理由があれば備考に書く

合否欄に書く語は、この4語のみです（集計のため）。迷ったら備考に書きます。実行したら、同じ日のうちに、合否・実行日・実行者・証拠を記入します。

② 不合格の切り分け: 何が間違っていたのか

不合格が出たら、「テスト」「実装」「仕様」のどれが古い・間違っているかを切り分けます。この案件の実例です（テスト結果.md 7.2）。

テスト期待 / 実測原因直したもの
I-136期待: 非公開の部活で、「予定」の開催に「申し込む」が出ない／実測: 出る画面側に、非公開の確認（is_active）が無かった実装を直した → 再実行で合格（2026-10-11）
I-057・I-058期待: 仕様どおりの文言／実測: 実装の文言が違う仕様の文言が、実装の文言と違っていた仕様の文言を実装に合わせて改訂し（PM の裁定、2026-10-11）、テストを追従 → 再実行で合格
I-061期待: 「中止」の通知でも「見る」で部活詳細へ進める／実測: 「見る」が出ない実装が、「中止」を「見る」の対象から意図的に外していた（MVP の範囲を絞るため）仕様（SP-45）に「MVP の範囲外」と明記して、実装と合わせた（PM の裁定、2026-10-11）。テストを追従 → 再実行で合格
  • どれを直すかは、実行した人が決めない。仕様に関わる変更は、決める人（PM）が判断し、記録に残します。
  • 原因が分かるまでは、「原因未確認」のままにします。実行中に、仕様に書かれていない挙動に当たったら、補って判定せず、その行は未実行のまま止めて報告します。

③ 記録のしかた

  • 証拠は evidence/test/ の該当する置き場へ。名前は <テストID>_<日付>_<実行者>_<連番>.<拡張子>（例: I-041_20261012_kurosu_01.png）。
  • 不合格の証拠も残す（上書きしない）。
  • 再実行したら、合否欄を最新にし、前回の結果を備考に残す。
  • 実行コマンド・環境・コミット ID を、証拠のログの先頭に書く。
  • 不合格は、テスト結果.md 7.2「不合格の追跡」に1行ずつ足す。修正が決まるまで残す。
  • 秘匿値・実在の個人情報が写っていないことを確認してから置く。
8

その後の工程: 自己評価 → TA の独立評価 → 相互レビュー → 修正

U・I・S を実行し終えたら、初回提出版をコミット ID で固定します（固定したあとに直したら、直したコミット ID と再実行の範囲を記録）。そのあとは、次の順番です（V字フロー規定.md 評価の節）。

初回提出版を固定（コミット ID）
   ↓
① 自己評価（チーム）   自分たちの要求・受入基準に照らして「できた／想定と違った」を書く
   ↓
② TA の独立評価        実装した人とは別の人が、承認済みの基準で評価する
   ↓
③ 相互レビュー         相手チームの指摘（指摘 ID は X-連番）。自己評価に「気づいていなかった点」を足す
   ↓
④ 修正 → 受入 A（ユーザーが合格を決める）
  • 自己評価が先です。外の評価を受ける前に、自分たちで「できた／想定と違った」を書きます。
  • 結果を見て、評価の基準を変えません。変える場合は、理由と影響を ADR に書き、人の再承認を受けます。
  • 受入 A-xx の合否は、ユーザー本人の言葉を欄に残します（AI が代筆して合格にしません）。

場面別ガイド: やること → 理由 → よくある失敗

「いま、何をすればいいか」を、場面から引く表です。5つの場面があります。

A. テストを企画する

やること理由よくある失敗
要件（F・N）と仕様（SP）から、S と I のテスト設計を書く（5章の型）テスト設計は、上流の文書と対で書くもの。根拠の ID（対応列）で、後から追える実装が終わってから、思いついた順に書く
★（重要な観点）は、正常系・異常系・境界値に分ける重複申込・権限・非公開情報などは、1つの確認では漏れる正常系だけで「確認した」とする
仕様に書いていない挙動は、足さずに報告する文書の穴をテストで埋めると、穴がそのまま見えなくなる「たぶんこうだろう」で期待結果を書く
完了条件を先に決める（9章④）終わりが決まっていないと、全件合格にこだわって終われない「全件合格」を暗黙の条件にする

B. 人に分担する

やること理由よくある失敗
Issue を層（U・I・S）ごとに分け、種類ごとに担当を決める（9章②）実行する人が層ごとに違う。同じ記録ファイルを同時に触る衝突も減る1つの Issue に全部入れて、誰が何をするか曖昧になる
実装した人とは別の人が、独立に評価する自分の実装を自分で評価すると、見落としに気づきにくい実装担当が、自分の I・S を独立評価として記入する
U の担当は、書いた人（git log）で確かめるIssue の割当は「その課題の担当」で、実装者とは限らない割当を実装者と取り違える
誰がいつ DB を使うかを、先に知らせる同じ DB を同時に操作すると、結果がぶれる他の人がテスト中の DB に、初期化をかける

C. 実行する

やること理由よくある失敗
準備のチェックリスト（4章④）を済ませてから始める環境や版が違うと、結果が再現しないコミット ID を控えずに実行する
U → I → S → A の順に回す（9章①）前段の不合格が、後段の原因になる前段が不合格のまま、依存する後段を「合格」にする
日付に関わるテストは、日付を固定し、実行時刻も記録する（11章）日本時間の早朝（0〜9時）は、UTC では前日。「今日」がずれる日をまたいでから再実行して、結果が変わる
データを消す操作は、まず --dry-run で確認する付け忘れると、接続先の全データが消える確認せずに、共有 DB で初期化する
秘匿値が画面・ログに写ったら、その証拠を置かないコミットすると、値の変更が必要になるパスワード欄が写ったスクショを、そのまま置く

D. 進捗を共有する

やること理由よくある失敗
層別の件数の表で見せる（合格／不合格／対象外／未実行）全体が一目で分かり、割合の根拠も示せる「だいたい終わった」と文章だけで伝える
合否の語は4語に固定し、空欄をゼロにする空欄が、書き忘れか未実行か分からなくなる「保留」「一部OK」など、4語以外を書く
未実行は合格に混ぜず、残す理由を書く（9章⑤）数字が実際より良く見えるのを防ぐ。次の担当が分かる偽 repo での合格を、実 DB の合格として報告する
数値は、元の記録（テスト結果.md）で確かめ、日付と版を付ける古い数字が独り歩きする（性能テストの追加で、行数が変わった）日付のない数字を、そのまま引用する

E. 不合格が出た

やること理由よくある失敗
不合格として、証拠を残す。期待／実測の差分を書く後から原因を追うための材料になる証拠を上書きする。差分を書かない
原因は推測せず、「原因未確認」と書く。7章の切り分け（テスト・実装・仕様のどれが古いか）を行う推測で直すと、別の不具合を作る確認せずに、テストの期待結果を実測に書き換える
修正後は、全件を通しで取り直した1本の証拠にする修正前と修正後の一部を継ぎ合わせても、「修正後に全件が通った」証拠にならない（実践ナレッジ 5.17）修正後に、落ちた件だけ再実行して足し合わせる
再実行したら、前回の結果を備考に残し、7.2 に行を足す何が・いつ・どう直ったかの履歴になる合否欄だけ書き換えて、前回の結果を消す
