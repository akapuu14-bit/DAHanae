ハイブの回し方（運用知）

1.1 役割分担

役担当仕事
god（りじちょー）統括人間の窓口。割り振り・レビュー・main反映。提案はするが決断は人間
takahiro設計5文書の要求〜設計、I/F契約、タスクバックログ、Issue草案
mirinフロント画面。今回は主にダッシュボード・ハブ・overviewのHTML
teraoBE/DB環境セットアップ、GitHub進捗管理のスクリプトとworkflow
kurosuテストテスト設計、横断レビュー
yamapi書記決定・学び・失敗をナレッジへ記録

1.2 基本ループ

提案 → 確認 → GO → 実装 → レビュー → 反映

  • 人間が決める箇所（スコープ裁定、実装開始、公開範囲など）は、必ず「提案」として出し、本人の回答（「Aで」「OK」など）を記録してから進める。
  • 実装後は godが成果物を再実行・差分確認してから main へ反映する（例: T-021〜T-023 は「変更ファイルが scripts のみ・app本体無傷・テスト再実行OK」を確認して合格にした）。

1.3 通信と台帳の使い分け

手段用途
inbox/（受信）自分宛ての依頼。着手時に全件読み、処理後 inbox/.done/ へ移す
outbox/（送信）他者への依頼・共有。自分のoutboxにだけ書く。他者のフォルダには書かない
memory.md自分の決定・学び・失敗の追記ログ
board.md共有の計画（自由記述）。godだけが書く
tasks.json共有のタスク台帳（todo / doing / blocked / done）と、完了時の result

1.4 委任の4部構成

依頼（outbox）の本文は、次の4つを必ず入れる。

  1. OBJECTIVE（目的）: 何のためか、読み手は誰か
  2. OUTPUT（成果物）: 置き場所とファイル名、章立て
  3. 道具・情報源: 事実を拾ってよい場所（創作させない）
  4. BOUNDARIES（境界）: 触ってよい範囲、やってはいけないこと（push禁止など）、DONE条件
次に活かす一言: 「何を作るか」だけでなく「どこまで触ってよいか」を依頼に書くと、越境が減る。

開発プロセスの型（V字）

2.1 流れ

5文書（要求 → 要件 → 仕様 → 設計 → テスト設計）
  → 対象版をコミットIDで固定
  → PMの承認を明示的に記録（実装計画のコミットかPR）
  → 実装（W3）
  → テスト・独立評価（W4）

2.2 今回の実績（順序と根拠）

  1. 要求（T-001）: 資料3種から R-01〜R-48 を抽出。資料間でMVPスコープが食い違うことを検出し、人間へ上申した。
  2. 要件（T-002）: F-01〜F-52 / N-01〜N-14。保留24項目を表にして人間が裁定（暫定案があるものは採用、#1検索の入口は現状維持、#10ケース企業規模は500名で確定）。
  3. 仕様（T-003）: SP-01〜SP-78。
  4. 設計（T-004）とテスト設計（T-005）: 仕様が固定されたので並行で作成した。
  5. テスト設計の作成中に、kurosuが仕様の穴を5件検出。4件を確定して仕様に反映（T-006）。1件はテスト対象外で修正不要。
  6. 5文書を「コミットのみ、実装は保留」として commit 9a6a20f で固定。

2.3 原則

  • 証拠なき完了報告は禁止。完了には、コミットID・テスト件数・実行結果などを添える。
  • 未決に依存する作業は止める。独立した承認済み範囲だけ進める。今回も、保留の裁定が出るまで仕様（T-003）は blocked にした。
  • 実装開始は、対象版（コミットID）と実装計画に対する、PMの明示的な承認記録がある場合のみ。
  • テスト設計から仕様の穴が見つかる。「テスト設計を並行で書く」ことは、仕様の品質確認にもなった。
次に活かす一言: 文書を先に固めると、「何が未決か」が表になって人間の判断が速くなる。
3

並行開発を衝突させない設計

3.1 きっかけ（失敗）

teraoとmirinが、同じ app/frontend/services/ を別のAPI（関数版とクラス版）で書いて衝突した。「実装計画だけでは自走困難」という実証になった。

3.2 対策: 自走用ドキュメントの3点セット

文書内容
I/F契約（I-F契約.md）services 5本・repositories 9本の関数シグネチャを1つに確定。関数ベースに統一（クラスは作らない）
タスクバックログWave0〜4、担当・依存・受入基準、所有境界（1ファイル1タスク）
環境セットアップ共有前提の手順（プレースホルダのみ、実キーは書かない）

型:

  • I/F契約: 呼び方（引数名・戻り値）を一つに決め、「契約にない呼び方は使わない」と明記する。
  • 1ファイル1所有者: 同じファイルを2つのタスクが触らないように、バックログの各タスクに所有ファイルを割り当てる。

3.3 「💡実装のコツ」を3か所に同じ内容で配る

落とし穴を1行で書いた「💡実装のコツ」を、次の3か所に同じ内容で置いた（T-024, T-025）。

  1. タスクバックログ.md（各Wave表の直後）
  2. GitHub Issue 本文の末尾（open 37件すべて）
  3. task_hints.json（37件）
  • 整合の確認: バックログ内の💡は37個で、task_hints.json と過不足なく一致。Issueへの追記は 追記37 / skip0 / notfound0。冪等（💡マーカーで判定）で実行した。
  • 内容の例: read_at IS NULL で未読を判定する、申込済みの判定は exists_active のみ、Streamlitの再実行による二重送信、太字は既読化前のデータで描画する、など。
次に活かす一言: 配布先が複数あるときは、元データ（json）を1つ決め、そこから各所を機械的に揃える。
4

進捗の見える化（作った仕組みと再現手順）

4.1 仕組み

  • GitHub Issue / Label / Milestone: タスク＝Issue。Labelは area / type / prio / wave、Milestoneは3つ。
  • PR「Closes #」による自動クローズ: PR本文に Closes #12 と書いてマージすると、Issueが自動でクローズされる。進捗報告の作業を別に発生させない。
  • Actions → Pages ダッシュボード: .github/workflows/dashboard.yml が scripts/gen_dashboard.py を実行し、HTMLを公開。担当者軸（担当者ごとの内訳）と締切軸（Milestoneごとの内訳）の2ビュー。期限・遅延バッジ（完了／遅延N日／本日締切／期限内／期限未設定、JST判定）付き。
  • overview.html（開発ロードマップ）: Wave0〜4のタイムラインと全37タスクの早見表。
  • 開発ハブ（hub.html）: 日々の入口。ダッシュボード・overview・ガイドへ導線を張る。

4.2 三者の役割分担（混ぜない）

場所役割性質
ダッシュボード数字（誰が・どれだけ・遅れているか）動的（自動更新）
overview地図（全体像・現在地）静的
タスクバックログ正本（受入基準・依存・所有境界）手で保守

4.3 再現手順（次のチームがコピーして使う）

正本は docs/github-管理セットアップ.md。要約:

# 1. gh を入れて認証（repoスコープ。remoteがSSHならプロトコルはSSH）
brew install gh
gh auth login

# 2. Label・Milestone を作る（Issueは作らない）
bash scripts/setup_github.sh

# 3. タスクIssueを作る（冪等・正式版はこちら）
bash 02_プロジェクト/bukatsu_concierge/実装ガイド/create_issues.sh

# 4. ダッシュボードを手動で起動して確認
gh workflow run dashboard.yml
  • Pages有効化: リポジトリ Settings → Pages → Source: GitHub Actions（この操作にはオーナー権限が必要だった）。
  • ワークフローの自動起動（push / schedule / issue）は、ファイルがデフォルトブランチ（main）に載ってから有効。featureブランチのままでは動かない。
  • 公開範囲: リポジトリがpublicなら Pages も公開。今回は人間が「公開PagesでOK」と判断し、掲載は進捗情報のみとした。Issue/PRに秘匿情報・実在個人情報を書かない約束を進捗管理ガイド6章に明記した。
次に活かす一言: 進捗は「報告する」のではなく、Issue と PR から「勝手に集計される」形にする。

ハマりどころ集（失敗と対処）

5.1 サンドボックス内で gh と git push（SSH）が失敗

原因
サンドボックスがTLS傍受・keyring不可・SSHを遮断している
対処
ghとpushはサンドボックス外で実行する。外向きの操作なので、人間の承認を得て行った

5.2 Pages有効化とadmin付与ができない

原因
個人リポジトリでは、コラボレーターにadminを付けられない。Pages有効化はオーナー権限が必要
対処
Pages有効化はオーナー（あかぷ）に依頼した。Issue作成とassignはwrite権限で足りるため、docsの「admin」表記を「write」に訂正した

5.3 依頼メッセージが配送されず bad- で戻った

原因
outboxのJSONが独自書式だった（bodyがオブジェクトなど）
対処
正しい書式に統一した。必須キーは次の10個。id（拡張子抜きのファイル名と一致）／conversation／from／to／act／subject／body（文字列）／hops／requires_reply／needs_human／created_at

5.4 「待機」の指示より先に、mirinが旧版UIを実装した（T-026、旧版は commit 9a05220）

原因
仕様がUI/UX込みで二転三転していた。確定GO前に発注した
対処
正直に報告させ、旧版は破棄して新版で作り直した。以後は確定GOが出るまで発注しない（hold運用）

5.5 AIが書いたコードが衝突し、破棄した

原因
teraoとmirinが同じ層を別のAPIで実装した
対処
方針を「実装は人間が各自」に転換し、I/F契約と1ファイル1所有者で再設計した（第3章）。破棄したコードは退避コピー0件で復元不可だが、方針が破棄だったので実害はなし

5.6 ダッシュボードが「足した」結果、見づらくなった

原因
機能追加を重ね、内訳が常時開き、0件セクションも並んだ
対処
T-023とT-027で整理した。内訳は既定で閉じる、0件セクションは見出しごと非表示、未アサインは別ブロックに分離。数値・集計は不変

5.7 大きめのUI依頼が二転三転した

原因
最初の指示に案がなく、作ってから確認した
対処
提案→確認を先に回し、確定してから発注する

補足（Issue二重化）: 横断レビュー（T-013）で、タスクIssueが setup_github.sh と create_issues.sh の両方で作られる二重化（重大）と、テスト設計が確定した仕様に追随していない矛盾（重大）を検出した。前者は create_issues.sh に一本化、後者はテスト設計を更新して解消（T-014〜T-016）。作った文書を、別の担当（kurosu）が横断で見る工程が効いた。

次に活かす一言: 失敗の多くは「確認前に動いた」か「境界が書かれていなかった」か「書式の不一致」。この3つを先に潰す。

2026-10-01〜10-04 の追記（記録日 2026-10-04。立ち上げ後、実装期に入ってからの失敗と学び。根拠は各項目の PR・commit と、末尾「出典」の追記分）

5.8 I-F契約に関数が無く、仕様どおりの画面を作れなかった（2026-10-04）

何が起きた
あかぷが画面の実装中に2件見つけた。① サイドバーの「部活の管理」は SP-01 で幹事・運営者に表示するが、get_role(employee_id, club_id=None) は is_admin しか見ないため、幹事を部活横断で判定できなかった。② S04 部活詳細に必要な読み取り関数 get_club_detail が I-F契約に無かった

対処
仕様外の補完ではなく「契約の穴埋め」と判断し、takahiro が I-F契約に関数を追加した（PR #90 is_organizer、PR #91 get_club_detail）。既存関数のシグネチャは変えない。god が実コードと突き合わせて検証した。2026-10-04 時点で、どちらもはなえの承認待ち（OPEN）

5.9 契約の文言修正がマージに間に合わず、契約と実装がずれた（2026-10-03〜04）

何が起きた

原因

対処

次に活かす一言

5.10 ローカルの main を基準にして、PR に関係ないコミットが混ざった（2026-10-03）

何が起きた
PR #69（hub.html の2行修正）に、未 push のローカルコミット 70f703d（messages_repo）が混入した。2026-10-04 には、ローカル main が origin/main より 53 コミット遅れていることも見つかった
原因
作業ブランチをローカルの main から切っていた
対処
git rebase --onto origin/main で混入を除いて force-push した。以後は origin/main から分岐し、PR 前に git diff --stat origin/main...<branch> で変更ファイルを確かめる（#86〜#95 で運用）
次に活かす一言
基準は常に origin/main。PR 前の差分確認を手順に固定する

5.12 PR 上で dashboard の deploy ジョブが毎回 fail する（2026-10-04 時点）

何が起きた
dashboard ワークフローは pull_request イベントでも動き、そのときの結果は毎回 failure だった。main への push では success だった。gh run list --workflow dashboard.yml の 2026-10-04 の12件では、pull_request 9件がすべて failure、push（main）3件がすべて success
原因
未確認。deploy ジョブが github-pages 環境へ配信する構成であることは確認したが、PR で失敗する理由までは調べていない
対処
PR 上の deploy の fail はマージ可否の判断に使わず、マージ後の main の実行結果で確かめる（mirin の記録。#95 のマージ後に build・deploy とも success）
次に活かす一言
「いつも落ちるチェック」は、理由が分かるまで記録して区別し、本物の失敗と混ぜない

次にやる人へのチェックリスト

立ち上げ順の要約。左から順に、前の項目が済んでから次へ進む。

  1. □ 始め方を選ぶ: 会話から始めるか、inputs/の資料から始めるか。個人かチームか、決定者は誰か。
  2. □ 人間の最初の回答を保存（修正した場合は理由も）。
  3. □ 5文書を作る（要求 → 要件 → 仕様 → 設計 ＋ テスト設計）。資料間の食い違いは人間へ上申する。保留は表にして裁定をもらう。
  4. □ 対象版をコミットIDで固定し、実装計画を書く。
  5. □ PMの明示承認を記録（実装計画のコミットかPR）。承認前に実装を発注しない。
  6. □ 進捗基盤を立てる: gh認証 → setup_github.sh → create_issues.sh → Pages有効化 → ダッシュボード確認（章4）。
  7. □ アサイン: Issueのassigneeを設定し、Milestoneを割り当てる。
  8. □ 実装ガイドを配る: I/F契約・所有境界・💡実装のコツ・環境セットアップ（章3）。
  9. □ 実装 → PR（Closes #）→ レビュー → マージ。ダッシュボードで進捗を確認する。
  10. □ 完了報告には証拠を付ける。作った文書は別担当が横断レビューする。
