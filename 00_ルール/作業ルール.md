# 作業ルール

チーム全員（りじちょー・スタッフ・Claude Code・受講生）が守る基本の規定。

## 1. 計画 → 承認 → 実装
1. 計画: 何を・なぜ・どう作るかを示す（実装計画に対象版・担当・根拠 ID・完了証拠）。
2. 承認: ユーザーの承認を待つ。承認前に作り始めない。合図は「OK」「Aで」「進めて」「決定」。
3. 実装: 承認後に作る。

## 2. 既存資産を先に読む
いきなり作らず、案件フォルダの 5 文書・`inputs/`・`01_ナレッジ/index.md`・`voice/` を先に読む。

## 3. 日本語・具体
回答・コメント・文書は日本語。コマンドはコピペで動く形で示す。Mac と Windows で違う場合は両方書く。

## 4. 作業範囲
作業対象はこのフォルダ配下。外のファイルを読む・書くときは、対象を示して承認を得る。

## 5. 完了報告は証拠つき
テスト結果・実行ログ・生成物のパス・本番 URL を添える。証拠なき完了報告は受け取らない。

## 6. 秘匿情報
`.env`・API キー・パスワードはコミットしない。ナレッジや文書にも書かない。`.env` は読まない・書かない・値を聞かない（変数名は `env.example` を見る）。OpenAI のキーは API 側の環境変数だけ。

## 6-2. 事故防止（Git）
- `main` に直接コミット・push しない。作業ブランチを切って PR にする
- `git push --force`・`git reset --hard`・`git clean`・`rm -rf`・`--no-verify` を使わない・提案しない
- TA（支援者）はコードを直接修正しない。PR コメントと回答まで

## 7. 役割の境界
- りじちょー: 壁打ち・計画・割り振り・最終確認。**決断はしない**（ユーザーが決める）。実装もしない。
- スタッフ: 割り振られた範囲だけを、文書どおりに作る。範囲外・未記載は止まって報告する（未決のまま進めても、未決の部分は作らない）。
- 書記: 学びと決定の記録。index / log の更新。
- 受講生: 個人回答の原文は本人が書く。採否・承認・受入は人が行う。
