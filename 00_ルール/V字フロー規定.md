# V 字フロー規定

```
要求 ──▶ 要件 ──▶ 仕様 ──▶ 設計 ──▶ 実装
  ▲         ▲         ▲         ▲        │
  │         │         │         └─ 単体 U ┘
  │         │         └───────── 結合 I
  │         └─────────────────── システム S
  └───────────────────────────── 受入 A（自己評価 → 他者評価）
```

スタートは要求定義。中心の問い「このアプリでダイエットに取り組みたい、使い続けたいと思うには、どんな利用体験が必要か」への個人回答から、チームの要求を作る。

## 上流 5 文書（ユーザーが書く。りじちょーが壁打ち。設計だけ AI が書き人がレビュー）

| 文書 | 答える問い | ID | 完成の条件 |
| --- | --- | --- | --- |
| 個人回答.md | 本人が AI と話す前に、誰が・何に困り・どうなれば嬉しいかを書く。対話後の変更と理由を追記 | — | 原文が上書きされていない。対話後の理由がある |
| 要求.md | 誰が、何のために、何ができると嬉しいか | R-xx、受入基準 | 使う人・困りごと・成功の定義が書かれ、「未決」が無い |
| 要件.md | 何を満たせば要求に応えたことになるか | F-xx／N-xx | 機能要件と非機能要件に ID があり、各要件に受入基準がある |
| 仕様.md | 具体的にどう振る舞うか | SP-xx | 入力・出力・画面・データ・エラー時の挙動が要件 ID と紐づく。主要導線は「UI 状態 → API → データ → 期待結果」の1行 |
| 設計.md | どう作るか（AI が書き、人がレビュー） | D-xx | 構成・データ・処理の流れが仕様の見出しか要件 ID に紐づく |
| テスト設計.md | どう確かめるか | A／S／I／U | 要件 ID ごとにテストケース（前提・操作・期待結果）がある。トレーサビリティ表がある |

## 既にある文書と ADR
- 既存の文書は `02_プロジェクト/<案件>/inputs/` に置く。りじちょーが先に読み、5 文書に写す。`.docx` は pandoc で md に変換してから読む。以降は md が正本
- ユーザーの決定は `ADR.md` に 1 行ずつ残す（起点・何を・なぜ・捨てた案・撤退ライン仮説）。各文書の「決定事項」は ADR の ID だけ
- 保留には確認する人・期限・確認事項・決定基準を書く

## りじちょーの壁打ちの作法
- 抜けている項目を **質問** で埋める。「○○はどうしますか」。一問ずつ
- 選択肢は **提案** してよい。「A（〜）と B（〜）があります。わたしは A を勧めますが、決めてください」
- **決断はユーザーの明示**で確定する（「Aで」「決定」）。確定したら該当文書の「決定事項」に書き戻す
- ユーザーが「任せる」と言っても、りじちょーは 1 つに絞って提示し「これで決定しますか」と聞く
- 曖昧な答え（「どっちも」「たぶん」）は決定として書かず、聞き直してから書く。実装言語・工程の省略・スコープ変更も、りじちょーが提案しユーザーが決める
- 個人回答の原文は上書きしない。AI が全欄を代筆した回答は本人の証拠にならない
- 要求.md の「何に困っているか」と「できると嬉しいこと」が食い違っていないか見比べ、矛盾があれば聞き直してから決定事項に書く

## ゲート
- 5 文書の「未決」欄が空になるまで、実装に進まない。実装計画・対象版を示し、人が実装開始を承認した記録を残す
- **ユーザーが「未決のまま進めて」と明示した場合は進む。ただしスタッフ（Takahiro／Mi-rin／Terao／Kurosu）と Claude Code は、未決の部分を補わず、その部分を作らずに「仕様に書かれていません」と報告して止まる。** 文書の穴がそのまま実装の穴になることを体験するための規定
- 週ごとの通過条件は `00_ルール/ゲート/W0〜W4.md`。TA・講師の指摘は ID 付きで受け取り、チームが判断して ADR に残す

## 左右の対応（各段にテストを置く）
| 上流文書 | テスト | 誰が設計 | 誰が実行・判定 |
| --- | --- | --- | --- |
| 要求（受入基準） | 受入テスト A-xx | りじちょーが補佐 | ユーザー（自己評価が先、TA・相手チームが後） |
| 要件 | システムテスト S-xx | りじちょー・Kurosu | Kurosu |
| 仕様 | 結合テスト I-xx | Takahiro | Kurosu |
| 設計 | 単体テスト U-xx | Terao / Mi-rin | 実装担当 |
テスト設計.md は上流と対で書き、末尾のトレーサビリティ表で要求 → 要件 → 仕様 → 設計 → テストをつなぐ。

## 下流（スタッフが作る）
- 設計: 仕様を構成・データ・処理に落とす。仕様に無い機能は足さない
- 実装: 設計どおりに作る。迷ったら止まって「仕様に書かれていません」と報告
- テスト: テスト設計どおりに実行し、結果（合否・ログ）を証拠として残す。W3 の単体・結合・システムの後に初回提出版をコミット ID で固定する
- 書記: 決定の履歴・学び・失敗を `01_ナレッジ` に返す

## 評価（W4）
- 自己評価が先: チームが自分たちの要求・受入基準に照らして、本番で「できた／想定と違った」と良い点・課題を書く
- 他者評価が後: TA の独立評価と相手チームの相互レビュー（指摘 ID `X-連番`）。自己評価に「気づいていなかった点」を足す
- 結果を見て評価基準を変えない。変える場合は理由・影響を ADR に書き、人の再承認を受ける

## 振り返り
案件の終わりに Keep / Problem / Try を 3 行ずつ。Try は次の案件の文書に反映する。

## 用語の対応（munder チーム向け）
りじちょーの定義（`.claude/agents/rijicho.md`）が使う用語を、この規定では次の意味で使う。munder には文書用の専用画面は無く、すべてチームリポの Markdown と QUEUE の会話、PR で行う。

| 用語 | この規定での意味 |
| --- | --- |
| 二入口 | 会話から始める（QUEUE で りじちょー の一問に答えて文書案を育てる）と、資料から始める（`inputs/` に置いた資料を りじちょー が先に読んで節案を作る）の2つの始め方 |
| 個人／チーム | 個人回答（本人が対話前に書く）と、チームでの採用・統合・保留・不採用の区別。決定者（PM）を実装計画に書く |
| 判断ポイント | 実装・評価・安全性に影響する判断（目的・基準・確認した事実・採用案・他案の扱い・見直す条件）。ADR に残す |
| 保留 | 決められない論点。確認する人・期限・確認事項・決定基準を書く。保留に依存しない作業は進めてよい |
| 版付き承認 | 5 文書のコミット ID（対象版）を実装計画に書き、PM が QUEUE か PR で「OK、進めて」と明示した記録。版が変わったら古い承認は使わない |
| 節の採用・確定 | りじちょーの案を読み、本人が「Aで」「決定」と明示して文書に取り込むこと。曖昧な返事は確定にならない |

munder を使わないチームも、同じことを Markdown の 5 文書と Claude Code、PR で行う。
